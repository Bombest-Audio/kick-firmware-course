Every few milliseconds the sound hardware runs out of audio and asks for more. The program has to hand it a fresh block before the old one finishes playing. Miss that deadline once and you hear a click. This lesson is about the code that lives under that deadline.

By the end you will be able to do four things. Compute the time budget for one block of audio. Explain what an `AudIO::Object` is and how one gets created and wired up. Trace one block from the audio device down through the object graph and back. And point at specific lines in the stock code that break the rules real-time audio depends on, and say how a custom OS could fix them.

<Aside type="note" title="Analogy">
A bakery with a conveyor belt that never stops. Every 10 milliseconds an empty tray reaches the end of the belt and a customer takes it. The baker has to fill each tray before it arrives. A tray that arrives half empty is a hole in the music. The baker can be the fastest in town and still fail, because one slow tray is enough. And the baker may not stop to look for flour in the storeroom, ask a coworker to unlock a drawer, or phone the supplier. Everything the tray needs must already be within arm's reach.
</Aside>

## What real-time audio means

Sound on a computer is a stream of numbers called samples. At 48 kHz there are 48,000 samples per second per channel. The KICK's audio device is configured for 48 kHz and 32-bit samples:

<CodeRef path="Linux/buildroot/board/freescale/imx8mm_var_som/rootfs_overlay/etc/asound.conf" line={27} expect="format S32_LE">

```text
format S32_LE
```

</CodeRef>

<CodeRef path="Linux/buildroot/board/freescale/imx8mm_var_som/rootfs_overlay/etc/asound.conf" line={28} expect="rate 48000">

```text
rate 48000
```

</CodeRef>

`S32_LE` means signed 32-bit integer, little-endian (ALSA's naming, general knowledge). The program does not hand the hardware one sample at a time. That would mean 48,000 wake-ups per second. It works in **blocks**, also called buffers or periods: a chunk of consecutive samples, such as 480 of them. The audio driver wakes the program once per block and says "fill this."

The arithmetic is short:

```text
time per block = frames per block / sample rate
per-frame budget = 1 / 48,000 s = about 20.8 microseconds
```

A **frame** is one sample for every channel at the same instant. For stereo, one frame is two samples.

| Frames per block | Time to the deadline at 48 kHz | Source of the size |
|---|---|---|
| 64 | 1.33 ms | Example only, my pick |
| 128 | 2.67 ms | Example only, my pick |
| 480 | 10 ms | Ceiling in `DawEngine.cpp`, and the library's DAW example |
| 960 | 20 ms | `BasicUsage` example, shown below |

```cpp

```

</CodeRef>

Three things follow from the table.

- **Bigger blocks are easier to hit and slower to hear.** A 480-frame block means a key press can wait up to 10 ms before the engine even starts on it (general knowledge about buffering latency). Smaller blocks cut that wait but shrink the deadline.
- **The worst block matters, not the average.** If your code takes 1 ms on most blocks and 15 ms on one, you hear one click. A fast average is no comfort.
- **One block is small in bytes.** 480 frames of stereo at 4 bytes per sample is 3,840 bytes. The cost is not the data. The cost is that everything must happen on schedule.

## Two threads and the rules for the second

Module 4 introduced the **message thread**: it runs the screen, and it may be slow for a moment without breaking anything but the picture. The **audio thread** is the other one. The audio driver calls into your code on it, once per block. JUCE's own comment on the audio callback says so plainly:

<CodeRef path="Kick/modules/engine/audio_engine/engine/mt_sample_player.h" line={55} expect="high-priority system thread">

```text
It will generally be called on a high-priority system thread, or possibly even
```

</CodeRef>

The rule for this thread is simple to say and hard to follow: **it must finish every block in bounded time, every time.** Anything whose duration you cannot bound is banned. These are the standard bans (general real-time audio knowledge, not from this repository):

| Banned on the audio thread | Why it can blow the deadline |
|---|---|
| Blocking locks | If another thread holds the lock, the audio thread waits for however long that thread takes. Worse, a low-priority thread can hold the lock while a medium-priority thread keeps stealing its CPU time. The audio thread, the most important one, then waits on the least important. That is called **priority inversion**. |
| Allocation and freeing (`new`, `delete`, `malloc`, growing a vector) | The allocator may take its own lock and may ask the kernel for more memory. Neither has a time limit. |
| File and network I/O | A disk or a socket answers when it answers. A flash read that takes 2 ms usually might take 40 ms once. |
| Logging (`printf`, `std::cout`, writing a log file) | It is I/O and often takes a lock on the stream. |

Notice what is not banned: arithmetic, reading and writing memory you already own, and **atomic** operations. An atomic is a variable the CPU updates in one indivisible step, so another thread never sees it half-written. Atomics never make a thread wait. The rest of this lesson is the story of what you use *instead* of the banned things.

## AudIO::Object: one box in the sound graph

The sound engine is a library called **AudIO** that lives in the `AudIO/` folder. Its basic building block is the **object**: one box that takes in some audio, does one job, and sends out some audio. A sine oscillator is an object. A mixer is an object. A reverb is an object.

### The interface

Every object promises to do two things. It must get ready, and it must process a buffer. That promise is a tiny interface:

<CodeRef path="AudIO/AudIO/Includes/IProcessable.h" line={7} expect="struct IProcessable">

```cpp
struct IProcessable
```

</CodeRef>

<CodeRef path="AudIO/AudIO/Includes/IProcessable.h" line={10} expect="virtual void process( Buffer">

```cpp
virtual void process( Buffer<float>& Buffer )                         = 0;
```

</CodeRef>

The `= 0` makes it a **pure virtual** function: the base class declares it and every concrete class must supply its own. The `Object` class builds on it:

<CodeRef path="AudIO/AudIO/Includes/AudioObject.h" line={11} expect="class Object : public IProcessable">

```cpp

```

</CodeRef>

An object is born knowing how many audio inputs, audio outputs and parameters it has:

<CodeRef path="AudIO/AudIO/Includes/AudioObject.h" line={16} expect="Object( uint32_t ninputs, uint32_t noutputs, uint32_t nparam )">

```cpp
Object( uint32_t ninputs, uint32_t noutputs, uint32_t nparam )
```

</CodeRef>

It also remembers a sample rate and a block size. The defaults are worth noticing. The sample rate defaults to 48,000 and the block size to 1, a placeholder until real values arrive:

<CodeRef path="AudIO/AudIO/Includes/AudioObject.h" line={86} expect="_sampleRate{ 48000 }">

```cpp

```

</CodeRef>

<CodeRef path="AudIO/AudIO/Includes/AudioObject.h" line={87} expect="_blockSize{ 1 }">

```cpp
uint32_t       _blockSize{ 1 };
```

</CodeRef>

The real values arrive through `prepareToPlay`, which the engine calls before sound starts, off the audio deadline:

<CodeRef path="AudIO/AudIO/Includes/AudioObject.h" line={39} expect="virtual void prepareToPlay( uint32_t samplerate, uint32_t blocksize )">

```cpp
virtual void prepareToPlay( uint32_t samplerate, uint32_t blocksize )
```

</CodeRef>

That split is the whole philosophy in miniature. **Allocate and set up in `prepareToPlay`. Only compute in `process`.**

The smallest useful object is a sine-wave generator. Its constructor says: zero inputs, two outputs, and as many parameters as the enum lists.

<CodeRef path="AudIO/AudIO/Objects/SineWave.h" line={21} expect=": Object( 0, 2, SineWave::kParamMax )">

</CodeRef>

Its `process` fills the output buffers. First it asks how many samples this block holds:

<CodeRef path="AudIO/AudIO/Objects/SineWave.cpp" line={150} expect="auto nSamples = buffer.getBlockSize();">

```cpp

```

</CodeRef>

Then one loop runs once per frame. Each pass takes one value from an oscillator and scales it by a smoothed amplitude:

<CodeRef path="AudIO/AudIO/Objects/SineWave.cpp" line={153} expect="m_amplitude.getNext() * m_lfo.process()">

Look at what this function does not do. It does not allocate. It does not lock. It does not print. It writes into memory that already exists. That is what a good audio-thread function looks like.

## The factory: how objects get created

Say the app wants "a SineWave" without the code asking for it knowing the class. The engine can create objects by **name**, through a registry called the `ObjectFactory`.

There are two halves. The first is registration. Each object's header ends with one macro line:

<CodeRef path="AudIO/AudIO/Objects/SineWave.h" line={45} expect={`REGISTER_OBJECT( "SineWave", SineWave );`}>

```cpp
REGISTER_OBJECT( "SineWave", SineWave );
```

</CodeRef>

The macro is defined in the factory header. It declares a file-scope `static` variable whose constructor does the registering:

<CodeRef path="AudIO/AudIO/Includes/ObjectFactory.h" line={11} expect="#define REGISTER_OBJECT( type, Object )">

```cpp
#define REGISTER_OBJECT( type, Object )                                   static AudIO::ObjectFactoryRegistration<Object> _##Object( type )
```

</CodeRef>

C++ constructs file-scope statics before `main` runs (general C++ knowledge). So by the time the program starts, every registered name is already in the table. The registration constructor stores a small function that builds one object on demand:

<CodeRef path="AudIO/AudIO/Includes/ObjectFactory.h" line={101} expect="std::make_unique">

```cpp
[]() { return std::make_unique<T>(); } );
```

</CodeRef>

The registry itself is a single global, built on first use:

<CodeRef path="AudIO/AudIO/Includes/ObjectFactory.h" line={34} expect="static ObjectFactory& Get()">

```cpp
static ObjectFactory& Get()
```

</CodeRef>

The second half is creation. `Create` looks the name up and calls the stored function. It holds a lock while it does:

<CodeRef path="AudIO/AudIO/Includes/ObjectFactory.h" line={61} expect="Create( const std::string& type )">

```cpp
std::unique_ptr<Object> Create( const std::string& type )
```

</CodeRef>

<CodeRef path="AudIO/AudIO/Includes/ObjectFactory.h" line={63} expect="autolock guard{ m_lock };">

```cpp
autolock guard{ m_lock };
```

</CodeRef>

That lock and the heap allocation inside `make_unique` are fine here, because creation is a message-thread job. A creation on the audio thread would break two rules at once. The design only works if nobody ever does that. Keep it in mind for the findings below.

The design calls the factory through a macro:

<CodeRef path="AudIO/AudIO/Includes/ObjectFactory.h" line={16} expect="#define CREATE_OBJECT( Type )">

```cpp

```

</CodeRef>

### Patching

Connecting one object's output to another's input is **patching**, a name borrowed from patch cables. The public call takes the source object, the source channel, the destination object and the destination channel:

<CodeRef path="AudIO/AudIO/Core/Design.cpp" line={433} expect="bool Design::patch( uint32_t srcid, uint32_t srcch, uint32_t dstid, uint32_t dstch )">

```cpp
bool Design::patch( uint32_t srcid, uint32_t srcch, uint32_t dstid, uint32_t dstch )
```

</CodeRef>

Underneath, each object is wrapped in a small record called `objectMeta`. It holds the object's buffer and a map of who it feeds:

<CodeRef path="AudIO/AudIO/Core/ObjectMeta.h" line={158} expect="_buffer;">

```cpp
Buffer<float>                                                           _buffer;
```

</CodeRef>

Patching records the link, then asks a queue to point the destination's input at the source's output memory:

<CodeRef path="AudIO/AudIO/Core/ObjectMeta.h" line={72} expect="::get().patchInput(">

```cpp

```

</CodeRef>

No audio is copied when you patch. Two buffers simply share a block of memory. After linking, the design refuses any connection that makes a loop, since a loop would mean an object waiting on its own output:

</CodeRef>

Then it marks the design **dirty**, which means "the run order may be stale":

<CodeRef path="AudIO/AudIO/Core/DesignImpl.cpp" line={160} expect="_dirty.store( true );">


</CodeRef>

### The run order

Objects must run in an order where every object runs after the ones feeding it. This is a **topological sort**, a standard graph algorithm (general knowledge). The result is a vector called `_dfs`, a name taken from the depth-first search that builds it:

<CodeRef path="AudIO/AudIO/Core/DesignImpl.h" line={133} expect="_dfs;">

```cpp

```

</CodeRef>

At every block the design walks that vector front to back and tells each object to process:

<CodeRef path="AudIO/AudIO/Core/DesignImpl.cpp" line={60} expect="for( auto obj : _dfs )">

```cpp

```

</CodeRef>

<CodeRef path="AudIO/AudIO/Core/DesignImpl.cpp" line={63} expect="process();">

```cpp

```

</CodeRef>

The record then hands its own buffer to the real object:

<CodeRef path="AudIO/AudIO/Core/ObjectMeta.h" line={45} expect="_object.process( _buffer );">

### Where the buffers come from

Audio buffers are not allocated one by one. The engine reserves one big static array at startup and carves it into fixed-size blocks:

<CodeRef path="AudIO/AudIO/Daw/DawEngine.cpp" line={21} expect="#define MEM_POOL_SIZE ( 2500 )">

```cpp
#define MEM_POOL_SIZE ( 2500 )
```

</CodeRef>

<CodeRef path="AudIO/AudIO/Daw/DawEngine.cpp" line={27} expect="float _audioPoolMemBuffer[( MEM_POOL_SIZE * BLOCK_SIZE )];">

```cpp
float _audioPoolMemBuffer[( MEM_POOL_SIZE * BLOCK_SIZE )];
```

</CodeRef>

That is 2,500 blocks of 480 floats: 1,200,000 floats, or about 4.8 MB at 4 bytes each. A comment above it warns that the array must be big enough for the worst-case design, because nothing grows it later. A fixed **memory pool** like this is the textbook answer to "no allocation on the audio thread." Getting a buffer means taking a free slot from a list you already own.

### How the message thread talks to the audio thread

The graph is edited from outside the audio thread: a screen adds an object, the user patches a cable. But the audio thread is the only one allowed to touch the live graph. The solution is a **queue**. The message thread drops a request in, and the audio thread picks it up at the top of the next block. The queue is declared with room for 64 requests:

<CodeRef path="AudIO/AudIO/Core/PatchQueue.h" line={106} expect="_queue;">

```cpp
SPSCQUeue<PatchData<T>, 64> _queue;
```

</CodeRef>

`SPSC` means single producer, single consumer: exactly one thread writes and exactly one thread reads. That restriction is what makes it possible to build the queue without any lock. I will explain how in the section on fixes.

## Where the stock code breaks the rules

I read the path from `DesignImpl::process` outward and looked for the four banned things. Everything below is from reading source. I did not run any of it, and I did not measure how long any of it takes on the device. That is why each citation carries the "Not verified on hardware" badge.

Some of this matches the codebase notes in `CONCERNS.md`. Where I rely on a note instead of my own reading, I say so.

### First, what the code gets right

The authors clearly knew the rules. Four things are done well:

- Graph buffers come from a preallocated pool (shown above).
- Edits that add patches go through a lock-free queue instead of a lock.
- A voice's state is an atomic, not a mutex-guarded field:

<CodeRef path="Kick/modules/engine/audio_program/synth/iSynthVoice.h" line={81} expect="state{ State::FREE };">

```cpp
std::atomic<State> state{ State::FREE };
```

</CodeRef>

- A voice's scratch buffer is a member, sized once, not a new buffer per block:

## Why it matters, and what a custom OS could fix

Most of the time none of the findings above shows up. The graph is stable, nobody is editing, and every block takes a fraction of its deadline. The trouble comes in bursts: right when the user drags a cable, deletes a track, or loads a project, which is exactly when the app is also redrawing, reading files and waking the kernel. Real-time bugs hide until the machine is busy. A stage that works 999 blocks in 1,000 sounds fine in the demo and clicks in front of the customer.

Here is how to fix each class of problem, written so a smart high-school reader can follow every step.

### 1. Never wait: lock-free queues

A queue between two threads normally needs a lock so they do not trip over each other. But the codebase already contains a queue that needs none. Here is `push` and `pop` in `SPSCQueue.h`, in plain words.

Picture a circular track with 64 numbered parking spaces and two markers. The **write marker** says where the producer parks the next car. The **read marker** says where the consumer will take the next car from. The producer only ever moves the write marker. The consumer only ever moves the read marker. Neither touches the other's marker, so nobody ever has to ask permission.

Push writes the data into the space first, and only then advances the write marker:

<CodeRef path="AudIO/AudIO/Core/SPSCQueue.h" line={16} expect="ringBuffer[oldWritePos] = dataIn;">

```cpp
ringBuffer[oldWritePos] = dataIn;
```

</CodeRef>

<CodeRef path="AudIO/AudIO/Core/SPSCQueue.h" line={17} expect="writePos.store(newWritePos);">

```cpp
writePos.store(newWritePos);
```

</CodeRef>

That order is the whole trick. The consumer can only see the car after the marker moves, and by then the car is fully parked. The markers are `std::atomic`, and the default atomic operations in C++ come with strong ordering guarantees that make this reliable (general C++ knowledge). The two markers:

<CodeRef path="AudIO/AudIO/Core/SPSCQueue.h" line={38} expect="readPos { 0 }, writePos { 0 }">

```cpp
std::atomic<size_t> readPos { 0 }, writePos { 0 };
```

</CodeRef>

The "full" check explains the 63 from Finding 4. The queue calls itself full when advancing the write marker would land on the read marker. That wastes one space on purpose, so that "full" and "empty" look different: a 64-space ring holds 63.

The rule that keeps it correct is exactly one producer and exactly one consumer. Two producers racing on the write marker would break it. So a custom OS would keep these queues and add three habits: check the return value of `push`, give each producer its own queue, and size the queue for the worst burst.

### 2. Never allocate: preallocate and recycle

Every banned allocation has the same cure: make the memory before the deadline starts. Allocate at startup, hand out pieces from a free list, and take them back instead of freeing them. The buffer pool does this. The missing piece is the objects themselves. Instead of letting the audio thread delete a removed object, the fix is a **trash queue**: the audio thread unlinks the object from the graph and drops its pointer into a queue, and the message thread, which has time, does the actual `delete`. The audio thread never frees anything.

### 3. Never reorganize live: swap, don't edit

The graph sort is the hard one, because the data structure is complex. The standard answer is to build the new run order off to the side, on the message thread, and then publish it with a single atomic pointer swap. The audio thread reads the pointer once per block and works on a consistent snapshot. The old snapshot must not be freed until the audio thread has moved on, and the trash queue from the last step handles that. The cost is double memory for the order vector. The benefit is that structural edits stop being a per-block risk.

### 4. Give the audio thread priority from the OS

Code discipline is half the answer. The other half is how the operating system schedules the thread. Two facts from the pinned tree, both from reading config files:

The app's service file gives it a low CPU weight against other services:

```text

```

</CodeRef>

The kernel config in the Buildroot build selects full preemption, not the real-time patch set:

<CodeRef path="Linux/buildroot/configs/KTKick_defconfig" line={17} expect="BR2_LINUX_KERNEL_CUSTOM_CONFIG_FILE">

```text

```

</CodeRef>

<CodeRef path="Linux/buildroot/board/freescale/imx8mm_var_som/linux-configs/Linux-defconfig" line={5} expect="CONFIG_PREEMPT=y">

```text

```

</CodeRef>

`CONFIG_PREEMPT` lets the kernel interrupt most of its own work to run something urgent. It improves response, but it is not the full real-time kernel, which bounds the worst-case delay much more tightly (general Linux knowledge). A custom OS aiming at the tightest latency could try three standard moves: run the audio thread under a real-time scheduling policy such as `SCHED_FIFO`, raise or remove the weight cap on the service, and build the kernel with the PREEMPT_RT patches. I have not tried any of them on this hardware. They are the usual list, not a tested recipe.

## Customization pointers

- **Add a new object.** Subclass `AudIO::Object`, implement `process` without allocating, and end the header with `REGISTER_OBJECT`. `SineWave.h` and `SineWave.cpp` are the template. Put anything that needs memory in `prepareToPlay`.
- **Move deletion off the audio thread.** Start in `DesignImpl::handleRemove` and `handleClearDesign`. Replace the `erase` and `clear` calls with pushes onto a trash queue drained by the message thread.
- **Stop patches from vanishing.** In `PatchQueue::push`, test the return value of `_queue.push` and fall back to something that cannot lose the request.
- **Choose a block size.** The ceiling is `BLOCK_SIZE` in `DawEngine.cpp`. The requested value lives in `AudIO_constants`, which you do not have. You would define your own.
- **Fix the scheduling.** The service file and the kernel config named above are the two places to start.
- **Check your build first.** The public AudIO folder is missing the JUCE wrapper and the constants module. I did not try to build it. Expect to supply the missing pieces.

## Words to know

| Term | Meaning |
|---|---|
| Real-time audio | Audio code that must finish every block before a hard deadline, every time |
| Sample | One number describing the sound pressure at one instant on one channel |
| Frame | One sample for every channel at the same instant |
| Block (buffer, period) | A group of consecutive frames the driver asks for in one call |
| Deadline | The time by which the next block must be ready, equal to frames divided by sample rate |
| Audio callback | The function the audio driver calls once per block, on the audio thread |
| Priority inversion | A high-priority thread stuck waiting for a lock held by a low-priority thread |
| Atomic | A variable updated in one indivisible step, so other threads never see it half-written |
| AudIO::Object | The base class for every box in the sound graph: inputs, outputs, parameters and a process function |
| ObjectFactory | A global name-to-constructor table used to create objects by name |
| Design | A container that owns objects, patches them together and runs them in order |
| Patch | A connection from one object's output to another's input |
| Topological sort | Ordering a graph so every object comes after the ones feeding it |
| Memory pool | A big block of memory reserved at startup and handed out in fixed pieces |
| SPSC queue | A single-producer, single-consumer ring buffer that needs no lock |
| Data race | Two threads touching the same memory with no ordering, where at least one writes. Behavior is undefined |
| Preemption | The kernel interrupting running work to run something more urgent |
