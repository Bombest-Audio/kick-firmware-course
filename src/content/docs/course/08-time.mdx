<Aside type="note" title="Analogy">
A conductor in front of a row of drummers. The conductor does not play. The conductor only counts, and splits each beat into 96 tiny beats. ## What a clock is

A sequencer needs to know "where am I in the song". It cannot ask in seconds, because tempo changes what a second means. It counts in **ticks**, small equal slices of a quarter note. The number of slices is the **PPQN**, pulses per quarter note.

The arithmetic is two lines:

```text
ticks per second = (BPM / 60) x PPQN
tick period      = 1 / (ticks per second)
```

At 120 BPM the song moves 2 quarter notes per second. With 24 PPQN that is 48 ticks per second, so one tick lasts 20.833 ms. With 96 PPQN it is 192 ticks per second, so one tick lasts 5.208 ms. More PPQN means finer placement of a note.

MIDI's own clock is fixed at 24 PPQN (general MIDI knowledge, not from this repository). It is a coarse beat that machines send each other. The sequencer inside the KICK counts finer than that.

Here is what 96 PPQN costs and buys at three tempos. The last column assumes the 48 kHz sample rate from Module 6:

| BPM | Quarter note | Tick period | Audio frames per tick at 48 kHz |
|---|---|---|---|
| 60 | 1000 ms | 10.417 ms | 500 |
| 120 | 500 ms | 5.208 ms | 250 |
| 240 | 250 ms | 2.604 ms | 125 |

At 120 BPM and 96 PPQN, one tick is exactly 250 frames of audio. Keep that number. It comes back when I talk about sample accuracy.

### Time signatures change the beat, not the tick

The tick stays one 96th of a quarter note. What changes is how many ticks make a beat and a bar. The formula divides four quarter notes by the time signature's bottom number:

<CodeRef path="AudIO/AudIO/Daw/DawTime.h" line={66} expect="(double)ppq * 4.0">

```cpp
constexpr double ticksPerBeat( int denominator, int ppq ) noexcept { return ( ( (double)ppq * 4.0 ) / (double)denominator ); }
```

</CodeRef>

The engine's tempo settings call it with `defaultPPQN`:

<CodeRef path="Kick/modules/engine/audio_engine/engine/mt_audio_transport.cpp" line={94} expect="ticksPerBeat( getDenominator(), defaultPPQN )">

```cpp
return AudIO::ticksPerBeat( getDenominator(), defaultPPQN );
```

</CodeRef>

<CodeRef path="Kick/modules/engine/audio_engine/engine/mt_audio_transport.cpp" line={99} expect="ticksPerBar( getNumerator(), getDenominator(), defaultPPQN )">

```cpp
return AudIO::ticksPerBar( getNumerator(), getDenominator(), defaultPPQN );
```

</CodeRef>

Work it out. In 4/4 a beat is 96 x 4 / 4 = 96 ticks and a bar is 4 x 96 = 384 ticks. In 6/8 a beat is 96 x 4 / 8 = 48 ticks and a bar is 6 x 48 = 288 ticks. At 120 BPM, 288 ticks of 5.208 ms is 1.5 seconds, which is what six eighth notes take.


</CodeRef>

It inherits from JUCE's high-resolution timer:

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.h" line={44} expect="juce::HighResolutionTimer">

### One millisecond, and a counter that adds up elapsed time

When the clock starts, it asks that timer for a callback every 1 ms:

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.cpp" line={59} expect="startTimer( 1 )">

```cpp
getMidiClock().startTimer( 1 );
```

</CodeRef>

1 ms is finer than a 5.208 ms tick. The timer fires about five times per tick at 120 BPM. The clock does not turn each firing into a tick. It measures elapsed time instead. First, the tempo becomes microseconds per quarter note:

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.h" line={110} expect="MICROS_IN_MINUTE / Tempo">

```cpp
static float tempoToMicros( float Tempo ) noexcept { return ( MICROS_IN_MINUTE / Tempo ); }
```

</CodeRef>

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.cpp" line={161} expect="tempoToMicros( Bpm )">

```cpp
microsPerQuarterNote = tempoToMicros( Bpm ); // In Micro-Seconds.
```

</CodeRef>

At 120 BPM that is 60,000,000 / 120 = 500,000 microseconds. Then it computes how many ticks fit in one millisecond:

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.cpp" line={66} expect="getMidiClock().getInternalPPQN()">

```cpp
sTickFactor    = ( (float)( mills * 1000 ) / (float)microSeconds ) * getMidiClock().getInternalPPQN();
```

</CodeRef>

`mills` is 1, so the factor is (1000 / 500,000) x 96 = 0.192 ticks per millisecond. That matches the 192 ticks per second I computed above.

On every timer callback the clock reads the wall time, multiplies the elapsed milliseconds by that factor, and quits early if less than one whole tick has passed:

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.cpp" line={232} expect="getMillisecondCounterHiRes">

```cpp
auto currTime  = juce::Time::getMillisecondCounterHiRes();
```

</CodeRef>

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.cpp" line={234} expect="sTickFactor * diffTime">

```cpp
auto diffTicks = ( sTickFactor * diffTime );
```

</CodeRef>

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.cpp" line={236} expect="diffTicks < 1.0">

```cpp
if( diffTicks < 1.0 )
```

</CodeRef>

Otherwise it adds the fractional tick count to a running total and reports the whole-number part:

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.cpp" line={241} expect="sTickCounter += diffTicks">

```cpp
sTickCounter += diffTicks;
```

</CodeRef>

<CodeRef path="Kick/modules/engine/audio_midi/source/CMidiClock.cpp" line={282} expect="(uint32_t)sTickCounter">

```cpp
onTick( (uint32_t)sTickCounter );
```

</CodeRef>

This is a sound way to avoid drift. The total is a real elapsed-time count, so a late callback does not lose time. The cost shows up in the next two paragraphs.

### What that does to the tick stream

I wrote a scratch C++ program on my laptop that repeats this arithmetic with a perfect 1 ms timer and 96 PPQN. It is not the firmware. It shows what the formulas do when the timer behaves.

At 120 BPM the program gets a callback about every 6 ms, not every 5.208 ms. The reason: 5 ms of elapsed time is 0.96 ticks, which is under 1, so it waits one more millisecond and has 1.152 ticks. Over 10 simulated seconds there were 1,666 callbacks, and the counter ended at 1,919 when the ideal is 1,920. So no drift. But in 253 of those callbacks the whole-number tick value jumped by 2, and a tick value was never reported. Each reported tick also arrived up to about one tick (5.2 ms) after its ideal time. At 240 BPM the same effect doubled: 506 of 3,333 callbacks skipped a value.

Two things follow. A downstream consumer must not assume it sees every tick value. And the clock itself adds timing error before any other thread touches the tick. The scratch results are about the formulas. A real timer adds its own lateness on top.

## Timing, jitter and why the audio thread matters

Add up where a sequenced hit can lose time, from the code and the general mechanics:

- **Clock granularity.** The timer reports in whole ticks, up to about one tick late in my scratch model. At 120 BPM that is up to 5.2 ms.
- **Timer wake-up lateness.** A 1 ms timer on a general-purpose Linux system wakes when the scheduler lets it (general knowledge). I did not measure this.
- **Event hand-off.** The tick thread wakes after the signal. How soon depends on the scheduler and, with no priority set, on whatever else is running.
- **The lock.** If an edit holds the sequence lock, the tick thread waits.
- **The block boundary.** The voice flips to RUNNING at some moment. The audio thread starts it at its next block. The block size is unknown, as Module 6 explained, but the engine caps it at 480 frames:

<CodeRef path="AudIO/AudIO/Daw/DawEngine.cpp" line={22} expect="( 480 )">

```cpp
#define BLOCK_SIZE    ( 480 )
```

</CodeRef>

At 48 kHz:

<CodeRef path="Linux/buildroot/board/freescale/imx8mm_var_som/rootfs_overlay/etc/asound.conf" line={28} expect="rate 48000">

```text
rate 48000
```

</CodeRef>

a 480-frame block is 10 ms. If that were the real block, a hit could wait up to 10 ms for the block edge. I use 480 as an example, not as a measurement.

The word **latency** is the average delay. The word **jitter** is how much that delay varies from hit to hit. Constant latency is usually fine, because you can compensate for it. Jitter is what makes a groove sound uneven. A hit that is 3 ms late, then 0 ms, then 5 ms, then 1 ms sounds sloppy even when the average is small. How small is small depends on the listener and the sound. People often quote a few milliseconds up to about 10 ms as where drummers start to hear timing wobble (general knowledge, not measured here).

### Why the audio thread is the better place for timing

The audio callback runs once per block, on a schedule the sound hardware sets. The audio hardware is the steadiest clock in the box: it consumes 48,000 frames per second against its own crystal (general knowledge, not measured here). If the sequencer counts in audio frames, its tempo is locked to that crystal, and a tick has a known frame position. At 120 BPM and 96 PPQN, tick N sits at frame N x 250. The sequencer can find every tick that falls inside the next block and give each note an offset in frames. A hit then lands on an exact frame, not at the next block edge plus scheduling noise.

A wall-clock timer on another thread counts a different clock. The two clocks drift, and the timer's callbacks are disturbed by anything else the CPU is doing. Hand-offs between threads add delay, and they add it unevenly.

The price of the audio-thread approach is the rule from Module 6: the sequencer would have to run with no locks, no allocation and no file or bus I/O. The note path in this code allocates vectors and, for CV, writes to an I2C bus. Moving it would mean rewriting those parts first. That is the design trade the stock code made. It kept the awkward work off the audio thread and accepted the timing error.

### What the gap means for syncing

- **Playing along with a DAW.** The DAW's tempo changes are ignored. Its Start does not start the KICK. You press play on both, by hand.
- **Drift.** Two free-running clocks never agree exactly. If the two differ by 0.01 percent, after 10 minutes they are 60 ms apart (600 s x 0.0001). Hand-started loops slide against each other.
- **Following gear.** A box that sends MIDI clock into the KICK gets no response. The KICK is only a note source.

## Why it is built this way

The shape makes sense for how this app grew. The sequencer, its UI and its programs were written as ordinary desktop JUCE code. A `HighResolutionTimer` is the easy way to get a steady beat on any platform, and it works the same on a laptop and on the box. A second thread keeps slow program code, with its allocations and its I2C writes, away from the timer. The running-total tick counter is a good idea: it avoids drift and lets consumers survive gaps if they loop over the ticks in between, as the track does.

What the design gives up is exactly the property a drum machine is supposed to have: timing locked to the audio clock. It also leaves external sync unconnected.

## Customization pointers

These are sketches. I have not built or run any of them.

### Implement external MIDI sync

1. **Catch the bytes early.** The handler at `mt_audio_manager.cpp:73` runs on the message thread after an async hop. Put the work in `handleIncomingMidiMessage`, which the source comments as running on the MIDI thread. Stamp each clock byte there with a monotonic clock.
2. **Count, do not act.** On a clock byte, increment an atomic pulse counter and store its timestamp. On Start, set an atomic flag. Continue and Stop get flags too. No allocation, no lock.
3. **Make the tick thread consume them.** Each time it wakes, it reads the counter. Internal ticks come from external pulses: 4 ticks per pulse, from the 96 over 24 ratio the class already computes. Between pulses, interpolate with the measured pulse spacing, averaged over several pulses so one late byte does not move tempo.
4. **Map transport.** Start calls `play( seq, true, true )` from the beginning. Continue calls `resume`. Stop calls `stop`. Song Position Pointer, if you want it, maps to `seek`.
5. **Reuse or replace.** `CMidiClock` already has the switch and a place for external ticks. Fix the zero-interval bug and the divide by zero first, or write a smaller class.
6. **Decide the tempo display.** While locked, the BPM on screen should show the measured tempo and ignore the stored one.

The risk: this design still sits on the tick thread. Its error budget is the thread's jitter. The sync would be loose, not tight. To tighten it, the same counter should be read from the audio callback.

### Sample-accurate scheduling

Count audio frames in the callback. Given the block start frame and the block length, compute which ticks fall inside, using the frame-per-tick figure from the table (250 at 120 BPM). Give each note-on a frame offset and let the voice start its read at that offset. This needs the lock-free hand-off described in Module 6, because notes would flow from the editing side to the audio thread through a queue.

### Clock out

For MIDI clock out, send the clock byte once every 4 internal ticks from wherever the tick is counted. For a pulse on a CV jack, toggle a gate channel once per pulse. Both inherit the jitter of the thread that sends them, so doing it from the audio-side tick counter is the version that sounds tight.

## Words to know

| Term | Meaning |
|------|---------|
| Clock | A source of regular counts that the sequencer uses to know where it is in the song |
| PPQN | Pulses per quarter note. How many ticks make up one quarter note |
| Tick | One count of the clock. In the KICK, 1/96 of a quarter note |
| BPM | Beats per minute. The tempo |
| Pulse | One MIDI clock byte. The standard sends 24 per quarter note |
| MIDI Start, Stop, Continue | MIDI realtime bytes that tell other gear to begin, halt or resume from where it halted |
| Transport | The state and controls for moving time: play, pause, stop, seek, loop |
| Sequence | A bar-based pattern made of tracks, each with notes and a program |
| Song mode | A queue of sequences, each played for a set number of repeats, one after another |
| High-resolution timer | A timer that tries to call back every millisecond or finer, on a thread of its own |
| Monotonic clock | A clock that only moves forward and never jumps, unlike wall-clock time. Right for measuring intervals |
| Latency | The delay between an intended time and the actual time |
| Jitter | How much the latency varies from one event to the next |
| Sample-accurate | An event lands on an exact audio frame, not just somewhere in the block |
| Swing | Delaying every second note of a pair to make a shuffle feel |
| Quantize | Snapping note times to a grid |
| Ratchet | Splitting one note into several quick repeats |
| Gate | A voltage that is high while a note is held and low otherwise |
| PLL | Phase-locked loop. A circuit or routine that follows an incoming rhythm and keeps its own count in step |
