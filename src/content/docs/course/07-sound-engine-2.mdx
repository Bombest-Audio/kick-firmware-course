**Module 7 of 12 &#183; about 40 minutes &#183; needs Module 6**

You hit a pad. A drum sound comes out. Between those two events sit three ideas that the code keeps apart: a program, a voice and a sample. Mix them up and the source reads like soup. Keep them apart and it reads like a plan.

This lesson picks up where Module 5 stopped, at the call that starts a note. I follow that note into the engine, down to the loop that reads audio from memory. Then I show how finished voices add up into a bus, and how an Airwindows effect gets onto an insert slot.

By the end you will be able to name the class behind each program type, trace a pad press to the line that starts a voice, say how pitch works in the sampler, and list the steps to add one more effect.

<Aside type="note" title="Analogy">
A jukebox room. A program is one jukebox model, with its own rules for what each button plays. A voice is one turntable arm that is spinning right now. A sample is the record. Pressing a button picks a record and looks for a free arm. If every arm that button may use is busy, nothing plays. The KICK engine works almost exactly like this, and the last rule is a real quirk, not a metaphor.
</Aside>

## Three words that look alike

The code uses "program", "voice" and "sample" in several ways. Here is the split I use for the whole lesson.

- **Program.** A kind of instrument slot. It decides what a note means. There is a model class on the message-thread side and an audio class on the audio side.
- **Voice.** One playing sound inside an audio-side program. It holds a position in a sample, a gain, and a few envelopes. It is borrowed from a pool and given back when it finishes.
- **Sample.** The word has three meanings. I name each one below, so you can tell them apart when you grep.

That is the right call for audio code: allocate up front, borrow later (general real-time audio knowledge, from Module 6). Notice the argument. Every voice gets the program's `master`, a shared bundle of atomic pitch and gain values. That detail matters again in the mixing section.

`getNext` belongs to the slice renderer. That is the sampler. Now I explain what it does and why.

### Sample rate, in one paragraph

A recording is a list of numbers. Each number is the air pressure at one instant. The sample rate is how many numbers per second (general knowledge). A file at 44100 Hz holds 44100 numbers for each second of sound. The output runs at a fixed rate. If a file's rate differs from the output rate, you must read the file at a different speed to keep the pitch right.

### Pitch by playback rate

To change pitch, change the read speed. Read twice as fast and every wave repeats twice as often, so the sound goes up one octave and lasts half as long (general knowledge). Read at half speed and it goes down an octave and lasts twice as long. There is no separate pitch control. Speed and pitch are the same knob here.

The code does exactly this. The read position is a `double`, so it can sit between two stored frames.

<CodeRef path="Kick/modules/engine/audio_file_manager/source/audio_sound_renderer.h" line={94} expect="double curPos{ 0.0 };">


### Interpolation: reading between frames

The position is rarely a whole number. At 10.25 the reader sits a quarter of the way from frame 10 to frame 11. It needs a value there, but only whole frames are stored. Interpolation is a rule for guessing the in-between value (general knowledge).

The code splits the position into a whole part and a fraction called `alpha`:

<CodeRef path="Kick/modules/engine/audio_file_manager/source/audio_sound_renderer.cpp" line={195} expect="alpha          = curPos - iPos;">

```cpp
alpha          = curPos - iPos;                                       \
```

</CodeRef>

The rule it uses is linear. A straight line between the two nearest frames:

<CodeRef path="Kick/modules/engine/audio_file_manager/source/interpolators.h" line={42} expect="return ( ( x0 * invAlpha ) + ( x1 * alpha ) );">

```cpp
return ( ( x0 * invAlpha ) + ( x1 * alpha ) );
```

</CodeRef>

With `invAlpha` defined one line above as one minus alpha:

<CodeRef path="Kick/modules/engine/audio_file_manager/source/interpolators.h" line={40} expect="const float invAlpha = 1.f - alpha;">

```cpp
const float invAlpha = 1.f - alpha;
```

</CodeRef>

At alpha 0.25 you get 75 percent of frame 10 plus 25 percent of frame 11. The renderer applies it to both channels with the slice gain:

<CodeRef path="Kick/modules/engine/audio_file_manager/source/audio_sound_renderer.h" line={76} expect="linearInterpolator( alpha, inL[m0], inL[m1] )">

```cpp
*pL = slice->gL * linearInterpolator( alpha, inL[m0], inL[m1] );
```

</CodeRef>

Linear interpolation is cheap and clean for small pitch moves. When you pitch up by a lot, it lets in aliasing: harsh, folded-back high frequencies (general knowledge). Higher-order rules, such as cubic, cost more and sound cleaner.

The header names a cubic rule as the preferred one:

<CodeRef path="Kick/modules/engine/audio_file_manager/source/interpolators.h" line={34} expect="#define PREFERRED_INTERPOLATOR ( INTERPOLATOR_CUBIC )">

```cpp

```

</CodeRef>

<Aside type="caution" title="My reading, not run on hardware">
The cubic and hermite functions exist in that header, but I found no call to them. The renderer line above calls the linear one directly. By my reading, `PREFERRED_INTERPOLATOR` is a wish, not a switch, and playback is linear at this commit. A grep for `PREFERRED_INTERPOLATOR` shows whether I missed a use.
</Aside>

### Gain staging and headroom

Gain staging means keeping the level sensible at every stage, so nothing is too quiet to hide in noise and nothing is too loud to clip. This part is general knowledge, not something the code proves.

- Adding two uncorrelated signals of equal level raises the level about 3 dB. Adding two identical signals raises it 6 dB. Eight loud hits on a bus can pass full scale.
- Inside the engine the math is floating point, so a sum above 1.0 does not clip. It only clips when it is converted to fixed-point integers for the converter (general knowledge about audio drivers).
- So the place to look for a clip is the last stage before the hardware, and any limiter you add belongs there.

The code gives one hint. A buffer class has a function named `compressOutputs`, which the name says would squash peaks. Its only call is commented out:

<CodeRef path="AudIO/AudIO/Includes/AudIOBuffer.h" line={251} expect="//compressOutputs();">

```cpp
//compressOutputs();
```

</CodeRef>

I found no limiter or soft clipper anywhere on the voice-to-bus path. Dense patterns with hot samples can sum past full scale. Whether that is audible depends on the later stages, which I cannot see in the public tree.

### Add one more effect

These steps come from the Acceleration pattern above. I did not build any of them.

1. Make a folder `src/MyFx/` under the Airwindows folder. Add `MyFx.h`, `MyFx.cpp` and `MyFxProc.cpp`.
2. In the header, declare `class MyFx : public AudioEffectX`. Add a parameter enum, state variables, and a `processReplacing` declaration.
3. In `MyFx.cpp`, write the constructor that passes the program and parameter counts to `AudioEffectX`. Add the parameter set, get and name functions.
4. In `MyFxProc.cpp`, write `processReplacing`. Read from the input arrays and write to the output arrays. They are the same memory.
5. In `airwindows.cpp` or `airwindows2.cpp`, add a namespace block like the Acceleration one: include the header, call `REG_AIRWIN( MyFx, SomeCategory )`, then include the two source files.
6. Nothing else needs to change. Both top-level files are already included by `AudIO_airwindows.cpp`, and the registration is a static object.
7. The category you pass becomes the label in the Inserts category list.

If you want the effect to build outside the shim, you need the VST types faked in the base header. If your effect uses a VST call the shim does not define, the compile fails there first.

## Trade-offs and rough edges

- **Two sampler stacks live in the tree.** The live one is `audio_program/synth` plus `audio_file_manager`. A second set of sampler classes sits under `engine/objects/sampler`. Its polyphony constant is 16:

<CodeRef path="Kick/modules/engine/objects/sampler/ISampler.h" line={25} expect="#define MAX_POLYPHONY_PER_OBJECT ( 16 )">

```cpp
#define MAX_POLYPHONY_PER_OBJECT ( 16 )
```

</CodeRef>

  The engine build file lists the modules it builds, and `objects` is not among them. The list runs from line 2 to line 10, and `audio_program` is on line 7:

<CodeRef path="Kick/modules/engine/CMakeLists.txt" line={7} expect="audio_program">

```text
audio_program
```

</CodeRef>

  Nothing outside the folder includes it. By my reading, the second stack is not built. I ran no build. Do not quote 16 as the real polyphony.
- **A full pad drops the hit.** The steal branch is empty. Short samples hide it. Long tails make it audible.
- **No limiter on the way to the bus.** Headroom is yours to manage.
- **Linear interpolation.** Cheap and fine for small moves. It aliases on big pitch-ups.
- **Keygroup is a stub** at this commit.
- **Missing glue.** The public tree has no `AudIO_juce`, and the audio interface header depends on it:

<CodeRef path="Kick/modules/audio_interface/audio_interface.h" line={17} expect="dependencies:       AudIO_juce">

```text
dependencies:       AudIO_juce
```

</CodeRef>

  So the link between the KICK and the AudIO audio device cannot be read here.

## Customization pointers

These are directions drawn from the code above. I did not build or run any of them.

**Add a program type.** Add a value to `MTProgramType`. Write a model class that derives from `MTIProgram`, and an audio class that derives from `ISynthObject`. Copy the three-line pattern from the drum constructor: build, `createObject`, `connectOutputTo`. Add a branch to `createProgram`. The `toString` and `fromString` helpers next to the enum, and any screens that switch on type, also need the new value.

**Add an effect.** The seven steps above.

**Replace the sampler.** The reader is the `ASliceRenderer` class, and the interpolation is one call in the renderer header. Swapping that call for a better rule is the smallest change. A bigger change is a new voice class that derives from `ISynthVoice` and reads its own audio. Leave the dead `objects/sampler` code alone until you know whether anything uses it.

## Words to know

| Term | Meaning |
|------|---------|
| Program | An instrument slot that decides what a note means. Has a model class and an audio class |
| MTIProgram | The model-side base class, backed by a ValueTree |
| ISynthObject | The audio-side base class for programs. It is an AudIO object |
| Voice | One playing sound, borrowed from a pool |
| Polyphony | How many voices may play at once, here counted per note |
| Slice | A window over a file with loop, tune and gain settings |
| Sound | The decoded file data in memory |
| Layer | One of up to four samples stacked on a pad |
| Mute group | Notes that cut each other off, like open and closed hats |
| Playback rate | How many stored frames the reader moves per output frame. Rate sets pitch |
| Interpolation | A rule that guesses a value between two stored frames |
| Aliasing | False high tones that appear when a signal is read too coarsely |
| Bus | A mixing point that adds its inputs, each with a gain |
| Insert | An effect slot on a program or bus |
| Gain staging | Keeping the level sensible at every stage so nothing clips or hides in noise |
| Headroom | The space between the current peak and full scale |
| Shim | A thin layer that lets old code run in a new setting |
