**Module 9 of 12 &#183; about 45 minutes &#183; needs Module 4**

You change a note's probability from 100 to 50. Three things must now agree. The screen must show 50. The sequencer must roll the dice against 50. The file on the flash must say 50 tomorrow. If each of them keeps its own copy of the number, they drift apart, and the bugs that follow are the hardest kind: the unit looks fine and sounds wrong.

The KICK avoids this with one tree of values that all three read. This lesson opens that tree. You will see its real shape, how edits become undo steps, how a value gets from a screen to the audio side, and what the code does when it saves.

By the end you will be able to follow one property from a widget, into the tree, into the sequencer and onto disk, naming each file and each thread on the way. You will also know which claims about a power cut the code supports and which it does not.

<Aside type="note" title="Analogy">
A whiteboard in a rehearsal room. Everyone in the band reads the same board, and nobody keeps a private setlist in their head. When one person changes a line, the others see it change. Every few seconds someone photographs the board. Undo is a stack of those snapshots: take the top one off and the board goes back. The stack is a simplification. The real undo list stores the reverse of each edit, not a full copy of the board. The photo part is close to true, though: the project file is the board written out as text.
</Aside>

## Why state needs one model

Three parts of the program care about the project at once.

- **The screens** draw it. A list view shows note rows. A knob shows a level.
- **The engine** plays it. The sequencer walks the notes and asks each one whether it should sound.
- **The disk** keeps it. A project must come back after a restart.

There are two ways to wire that up. In the first, each part keeps its own data and copies changes to the others. That is a lot of copy code, and every missed copy is a bug. In the second, there is one place where the data lives. Everyone reads it there, and every edit goes through it. Programmers call that place the **single source of truth**. The KICK takes the second route.

The price is that the one place must be safe to touch from several threads, and it is not, by itself. A large part of this lesson is about that gap.

## ValueTree in plain terms

JUCE ships a data structure called a **ValueTree**. Think of one XML element. It has a type name, any number of named properties, and any number of children, which are ValueTrees too. A property holds a simple value such as a number, a string or a flag. That is the whole model (general JUCE knowledge).

Two more facts matter.

- **A ValueTree variable is a handle.** Copying the variable does not copy the data. Both variables point at the same node. So the engine, a screen and the file saver can each hold a handle and all see the same edit (general JUCE knowledge).
- **Listeners.** Code can register to be told when a property changes, or a child is added, removed or reordered. The call happens right away, on the thread that made the change (general JUCE knowledge).

Names for node types and properties are `juce::Identifier` objects. The KICK declares them all in one header with a macro, so a typo becomes a compile error instead of a silent new property:

## CachedValue: typed access to a property

A property is stored as a loosely typed value. Reading `probability` as an integer, with a default when the property is missing and a clamp to a legal range, is something every reader would otherwise redo by hand. JUCE has a helper, `CachedValue<T>`, for this. The KICK carries its own adapted copy, with one added feature:

<CodeRef path="Kick/modules/common/source/kick_CachedValue.h" line={62} expect="onValueChange">

```cpp
sigslot::signal<> onValueChange = {};
```

</CodeRef>

The added feature is that signal. Other code can connect to it and hear about a change without being a ValueTree listener itself.

A `CachedValue` does three jobs.

1. **It remembers the value in its real type.** Reading it is a plain member read, with no lookup.
2. **It supplies a default when the property is missing.** Here is the read path:

<CodeRef path="Kick/modules/common/source/kick_CachedValue.h" line={211} expect="getPropertyPointer( targetProperty )">

```cpp
if( const juce::var* property = targetTree.getPropertyPointer( targetProperty ) )
```

</CodeRef>

<CodeRef path="Kick/modules/common/source/kick_CachedValue.h" line={214} expect="return defaultValue;">

```cpp
return defaultValue;
```

</CodeRef>

3. **It keeps itself fresh.** It is a tree listener, and when its own property changes it refreshes its copy:

<CodeRef path="Kick/modules/common/source/kick_CachedValue.h" line={220} expect="forceUpdateOfCachedValue();">

```cpp
forceUpdateOfCachedValue();
```

</CodeRef>

The type argument can also clamp. A note's probability is declared as a `CachedValue<MidiConstrainer>`, which forces every value into the MIDI range:

<CodeRef path="Kick/modules/engine/interface/source/mt_audio_interface_types.h" line={665} expect="probability;">

```cpp
CachedValue<MidiConstrainer>    probability;
```

</CodeRef>

The default is the part to remember for later. Because a missing property reads as its default, a file written before a field existed still loads. That is the closest thing this code base has to a migration strategy, and the customization section builds on it.

## Undo: edits as transactions

An **UndoManager** keeps a list of edits so they can be reversed. The edits are grouped into **transactions**. One undo step reverses one transaction. A transaction can hold many small edits, such as dragging a slider through twenty values.

When you pass an UndoManager to `setProperty`, JUCE records an edit object holding the old and new values. Pass `nullptr` and nothing is recorded (general JUCE knowledge). That explains why you saw `&undoManager` in every setup call above, and `nullptr` in the `getOrCreateChildWithName` calls: creating the empty child is not an edit the user made, so it stays out of the history.

### Where one step ends and the next begins

JUCE adds each recorded edit to the current transaction until someone calls `beginNewTransaction` (I checked this against the `UndoManager::perform` source in a JUCE 8.0.8 checkout, not the JUCE version the KICK pins, which is not in the repository). So the code has to draw the lines itself. The KICK's `CachedValue` does it on every write:

<CodeRef path="Kick/modules/common/source/kick_CachedValue.h" line={135} expect="beginTransactionForUndo();">

```cpp
beginTransactionForUndo();
```

</CodeRef>

<CodeRef path="Kick/modules/common/source/kick_CachedValue.h" line={136} expect="targetTree.setProperty(">

```cpp
targetTree.setProperty( targetProperty, juce::VariantConverter<Type>::toVar( newValue ), undoManagerToUse );
```

</CodeRef>

So each assignment through a `CachedValue` is its own undo step. Other code skips the helper and writes to the tree directly. The list-edit screen does this when you change a note's probability:

<CodeRef path="Kick/modules/kick_ui/modes/kick_ListEdit.cpp" line={452} expect="mt::IDs::probability">

```cpp
if( vt.isValid() ) vt.setProperty( mt::IDs::probability, V, &mt::getAudioInterface().getUndoManager() );
```

</CodeRef>

That line passes the manager but does not begin a transaction. By the JUCE rule above, a run of such edits can merge into whatever transaction was already open. I read it that way and did not run it, so treat "may merge" as my reading. It is a good place to test on a real unit: change three values in the list view, press undo once, and see how many come back.

### What undo actually does to the rest of the program

Undo does not restore a snapshot of the program. It replays property changes backwards. Each replayed change fires the same listeners as the original edit. That is why a derived value stays correct. A track keeps a scaled copy of its level, and it recalculates when the `level` property changes:

<CodeRef path="Kick/modules/engine/audio_engine/engine/mt_audio_track.cpp" line={160} expect="levelScaler = ( level.get() * MIDI::SCALER );">

```cpp
levelScaler = ( level.get() * MIDI::SCALER );
```

</CodeRef>

The rule that follows: derived data must be rebuilt from a listener, not at the place where the user's edit happens. If a derived value is only set in the button handler, undo will skip it and the program will disagree with itself.

## How state reaches the audio side

Here the gap from earlier opens. A ValueTree is not safe to use from several threads at once (general JUCE knowledge). The audio thread has strict rules: no locks, no memory allocation, no waiting (Module 6). So the audio side cannot simply read the tree. The code uses three roads, and one of them has a trap.

The Module 6 lesson also covers a fourth road, the lock-free queue for graph edits. I leave that one there. The public `AudIO/` folder is partial, so for anything past the point where a value enters the graph I stop at the code under `Kick/` and send you to Module 6 and Module 7.

### Road one: atomic mirrors

`mt::Atomic<T>` is a wrapper holding a plain `std::atomic<T>`. It binds that atomic to one tree property:

<CodeRef path="Kick/modules/common/source/kick_atomics.h" line={141} expect="new VTPropertyValueSource( Tree, Property, Undo, true, DefaultValue )">

```cpp
value.referTo( juce::Value( new VTPropertyValueSource( Tree, Property, Undo, true, DefaultValue ) ) );
```

</CodeRef>

The `true` is the "update synchronously" flag. The source forwards a property change to the wrapper using that flag:

<CodeRef path="Kick/modules/common/source/kick_atomics.h" line={58} expect="sendChangeMessage( updateSynchronously );">

```cpp
sendChangeMessage( updateSynchronously );
```

</CodeRef>

When it fires, the synchronizer copies the new value into the atomic:

<CodeRef path="Kick/modules/common/source/kick_atomics.h" line={102} expect="fromVar( value.getValue() )">

```cpp
atomic = juce::VariantConverter<Type>::fromVar( value.getValue() );
```

</CodeRef>

The audio side reads with a plain atomic load:

<CodeRef path="Kick/modules/common/source/kick_atomics.h" line={169} expect="Type get() const { return atomic.load(); }">

```cpp
Type get() const { return atomic.load(); }
```

</CodeRef>

A real reader is the drum voice. In its per-block `process`, it loads the master gains at the top:

<CodeRef path="Kick/modules/engine/audio_program/synth/drum_voice.cpp" line={165} expect="master.gainL.load()">

```cpp
const auto masterGainL      = master.gainL.load();
```

</CodeRef>

That is the whole trick. The writer pays the cost (a tree write plus an atomic store). The reader pays almost nothing. Which thread does the store? With the synchronous flag, the thread that wrote the property does it, because I read no hop to another thread in these lines. So if the tree is written from a worker thread, the mirror updates on that worker thread. The atomic makes that safe for a single number.

Notice one limit. The pan and gain mirrors also recompute two derived atomics, `gainL` and `gainR`, in a callback. Those are two separate atomics. A reader could in principle see one updated and one not for a block. I did not test whether that is audible.

### Road two, and its trap: AtomicString

There is a string twin of the wrapper, `AtomicString`. The name promises more than the code delivers. Look at its storage:

<CodeRef path="Kick/modules/common/source/kick_atomics.h" line={250} expect="juce::String            atomic;">

```cpp
juce::String            atomic;
```

</CodeRef>

It is a plain `juce::String`, not an atomic. Nothing makes it safe to read on one thread while another thread assigns to it. Treat `AtomicString` as a convenience for the message thread, and never read one on the audio thread. The settings structs use it for things like the saved project name and the Wi-Fi fields, which are read from the UI.

## What survives a power cut

I will only claim what the code shows, and I will say where the claim stops.

**What the code shows.**

- A save serializes the tree and calls `replaceWithText` (kick_xml_manager.cpp, lines 94 to 97, cited above).
- With autosave on, the gap between an edit and the next write is at least the timer delay, 1.5 seconds by default. Edits made in that window exist only in memory.
- With autosave off, edits wait for the Save button or for a project close.
- I found no backup copy of the previous file and no check that a loaded file parsed.

**What JUCE does underneath (general knowledge, not the KICK repository).** I read the JUCE 8.0.8 source in a local checkout. `File::replaceWithText` writes the text to a hidden temporary file in the same folder, then swaps it in with a rename. The KICK's pinned JUCE version is not in this repository, so the details may differ. Rename on one filesystem is atomic on Linux (general POSIX knowledge), which means a crash during the write should leave either the old file or the new one, not half of each. In the JUCE path I read, the temporary file's close does not call `fsync`, so whether the new bytes reached the flash before the rename did is up to the filesystem.

**Where my claim stops.** I cannot tell you what the ext4 filesystem does with that ordering when power drops mid-write. I did not test a power cut on a unit. Treat "old or new file, never half a file" as what the design intends, and "the newest edits can be lost" as a given. Whether a zero-length file can appear is a question for a real unit and a fault-injection test.

<Aside type="caution" title="Not verified on hardware">
Everything about timing and power loss here comes from reading source. I did not run the app, time a save, or cut power. The paths come from the code and the mount units; I did not check them on a unit.
</Aside>

## Why it is built this way

The design makes a clear trade. Putting everything in one ValueTree gives you three things for free: a save format (the tree is XML), an undo system (edits record themselves), and change notification (listeners). The cost is that the tree is not thread-safe, so every audio-facing value needs a separate mirror, and every mirror is another place for a bug. The three roads above are the price of that choice.

The save design has a similar trade. Writing the whole project as one text file is simple and easy to inspect. It also means every save rewrites the full project, and a bigger project costs more per save.

## Customization pointers

- **Add a field to a note.** Declare an id with `DECLARE_ID`. Add a `CachedValue` member to `MTNote` and bind it in `MTNote::referTo` with a default, next to line 550. Write it in `MTNoteUtil::createVT`. Because a missing property reads as its default, old files keep loading. Start a transaction when your widget writes, or your change will merge with the one before it.
- **Bump a version and migrate.** The hook is `projectManager::loadOrCreate`, right after the `Project` node check at line 71 of `project.cpp`. Read the old version from the node, convert the tree, then write the new version. Nothing reads the version today, so you are adding the first reader. Keep copies of the demo files as test inputs.
- **Make autosave default on.** Change the default at the `Autosave` attach line in `kick_settings.cpp` (line 92 above). Check the static flag as well, since two switches exist.
- **Make saves safer.** Copy the old file aside before `replaceWithText`, and check the tree is valid after `fromXml`. Then test with a power-cut rig.
- **Store sample paths relative to the project.** The project folder is set up in `MTAudioAssetManager::setRootFolder`. Convert on add, convert back on load.
- **Make a mirror honest.** Replace `AtomicString` with a design that does not claim to be atomic, or use it only from the message thread.

## Words to know

| Term | Meaning |
|---|---|
| State | The data that describes the current project and settings: what a screen shows, the engine plays and the disk keeps |
| Single source of truth | One place where a piece of data lives. Everything else reads it there |
| ValueTree | A JUCE tree of nodes. Each node has a type, named properties and child nodes, and listeners can watch it |
| Identifier | A JUCE name type used for node types and property names |
| Property | One named value stored on a node |
| Listener | Code that registers to be told when something changes |
| CachedValue | A typed wrapper over one property, with a default and a local copy of the value |
| UndoManager | The JUCE object that records edits so they can be reversed |
| Transaction | A group of edits that undo together as one step |
| UndoableAction | A custom edit that knows how to apply and reverse itself, used when the data is not a property |
| Atomic | A value that can be read and written by two threads without a lock. `std::atomic` in C++ |
| Mirror | A small atomic copy of a tree property, made for the audio side to read |
| Autosave | A timer that writes the project after a change. Throttled here, not debounced |
| XML | A text format of nested elements. The project and settings files use it |
| Atomic write | Writing a file so that readers see the old version or the new one, never a half-written file. Usually a temporary file plus a rename |
| Mount | Attaching a disk partition to a folder path so files appear there |
| Overlay | A mount that shows a writable layer on top of a read-only folder |
