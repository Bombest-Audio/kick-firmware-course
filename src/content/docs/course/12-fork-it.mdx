**Module 12 of 12 &#183; about 40 minutes &#183; needs Modules 3, 4 and 7**

You have read the whole machine. Now the real question: can you change it and run your change?

This lesson is the plan, not the proof. I have not built any of it. I compiled nothing for this lesson, I ran no CMake, and every code sketch below is design, not built. What I did was read files at the pinned commit with `git show` and `grep`, and check every cited line. Where I guess, I say so.

By the end you will be able to list exactly which pieces a fork must write before it can compile, say what each piece has to provide, sketch the three kinds of change this course prepared you for, and explain in plain words what the AGPL-3.0 asks of you when you share the result.

<Aside type="note" title="Analogy">
You inherit a family recipe binder. Most pages are there and readable. Four pages were torn out because the printer would not let the family reprint them. The dishes that need those pages cannot be cooked as written. But the other pages say "add the stock from page 12", so you can work out what page 12 must have been, and write your own. That is a fork today. You rebuild the torn pages, then you start inventing new dishes.
</Aside>

### What I conclude

The simulator was written for an older version of the input path. Treat it as a design to copy, not a tool to run. The better route is the one Module 5 described as Option A: skip the wire, build a packet struct yourself, and fire the real dispatch signal from the message thread. You get a simulator by writing about a hundred lines that feed the right signal, not by fixing the old one.

Two smaller notes. The build pulls its own JUCE and patches it:

<CodeRef path="Kick/3rdParty.cmake" line={14} expect="7.0.12">

```cmake
set(JUCE_GIT_TAG           7.0.12)
```

</CodeRef>

The patch file name is keyed to that tag, and a failed patch stops configure:

<CodeRef path="Kick/3rdParty.cmake" line={56} expect="Failed to apply patch to JUCE">

```cmake

```

</CodeRef>

So do not point the build at a newer JUCE you already have on disk and expect it to work. The patch targets 7.0.12. The Apple deployment target is fixed at 12.0:

```cmake

```

</CodeRef>

## The stand-in plan

A stand-in is code you write to fill a hole, so the rest of the program can compile and run. You cannot copy the original, because you do not have it. But you have every caller. The callers tell you what the hole must hold.

The method is plain:

1. `grep` for every use of the missing name.
2. For each use, write down the type it needs, whether it must be a compile-time constant, and the operations it calls.
3. Build the smallest thing that satisfies all of them.
4. Mark every value you chose without evidence.

I did steps 1 and 2 for four holes. Step 3 is yours. Every value I propose is a guess unless I cite a line.

This module supplies numbers. The callers use them in four ways.

</CodeRef>

<CodeRef path="Kick/modules/engine/audio_engine/engine/mt_audio_manager.h" line={109} expect="AUDIO_NUM_SEND_RETURNS">

**MIDI range and scale.** The `MIDI` names are used about 230 times across the tree. A gain conversion pair shows what the three core names must do. One direction multiplies by a scale:

<CodeRef path="Kick/modules/common/source/kick_common_utils.cpp" line={50} expect="return ( MIDI::SCALER * MidiValue );">

</CodeRef>

<CodeRef path="Kick/modules/common/source/kick_common_utils.cpp" line={55} expect="jlimit( MIDI::MIN, MIDI::MAX">

</CodeRef>

A comment next to the first use gives away the intent:

<CodeRef path="Kick/modules/common/source/kick_common_utils.cpp" line={38} expect="// (MidiLevel / 127 )">

```cpp

```

</CodeRef>

That comment, plus the two functions being inverses of each other, makes `MIN = 0`, `MAX = 127` and `SCALER = 1/127` the consistent choice. Full range of a MIDI data byte is 0 to 127 (general knowledge). That is a deduction from two call sites and a comment, not a quote of the original.

### Stand-in 2: `AudIO_juce`

This module holds `AudioDevice`, the class that connects JUCE's audio hardware to the AudIO engine. Module 6 flagged it. Here is what the callers need.

The audio manager builds one device with an input count, an output count and a name:

<CodeRef path="Kick/modules/engine/audio_engine/engine/mt_audio_manager.cpp" line={56} expect={`make_unique<AudioDevice`}>

```cpp

```

</CodeRef>

It hands the device to the engine as a pointer:

<CodeRef path="Kick/modules/engine/audio_engine/engine/mt_audio_manager.cpp" line={60} expect={`engine.addAudioDevice( "Master", dm.get(), true );`}>

```cpp
engine.addAudioDevice( "Master", dm.get(), true );
```

</CodeRef>

The engine function takes the AudIO device interface:

<CodeRef path="AudIO/AudIO/Daw/DawEngine.cpp" line={180} expect="IAudioDevice* device">

```cpp
bool DawEngine::addAudioDevice( const std::string& name, IAudioDevice* device, bool /*master*/ )
```

</CodeRef>

So `AudioDevice` must derive from `AudIO::IAudioDevice`. That interface has four pure virtual functions. Here is the first:

<CodeRef path="AudIO/AudIO/Includes/IAudioDevice.h" line={37} expect="virtual void start( uint32_t samplerate, uint32_t blocksize ) = 0;">

```cpp
virtual void start( uint32_t samplerate, uint32_t blocksize ) = 0;
```

</CodeRef>

The others are `resume`, `pause` and `stop`. The base class also supplies a protected `process` that hands a buffer to the engine:

<CodeRef path="AudIO/AudIO/Includes/IAudioDevice.h" line={55} expect={`virtual void process( Buffer<float`}>

```cpp
virtual void process( Buffer<float>& buf )
```

</CodeRef>

That is the hook your JUCE callback must call, once per block, after copying input samples in. After it returns, you copy the buffer's output side to the JUCE output channels. That is my reading of the design from Module 6, plus general JUCE knowledge about audio callbacks.

There is one more caller. The audio manager asks the device for JUCE's device manager:

<CodeRef path="Kick/modules/engine/audio_engine/engine/mt_audio_manager.cpp" line={303} expect={`getJuceAudioDeviceMgr()`}>


```cpp
// WarmProc.cpp   (design, not built, not compiled)
void Warm::processReplacing(float **inputs, float **outputs, VstInt32 sampleFrames)
{
    float* in1  = inputs[0];
    float* in2  = inputs[1];
    float* out1 = outputs[0];
    float* out2 = outputs[1];

    const double drive = 1.0 + A * 9.0;        // A is the 0..1 knob
    const double norm  = 1.0 / tanh(drive);    // keeps a full-scale peak at full scale

    while (--sampleFrames >= 0)
    {
        *out1 = (float)(tanh(drive * *in1) * norm);
        *out2 = (float)(tanh(drive * *in2) * norm);
        in1++; in2++; out1++; out2++;
    }
}
```

A few rules for the order:

- **Simulator first means the goal, not the first task.** The first real work is the stand-ins. Do them one at a time and compile after each. When the first one lets one more module compile, you have evidence the method works.
- **One change at a time.** Config switches interact (Module 3). A fork with five changes and one failure teaches you nothing.
- **Pin your base.** Fork from the pinned commit, write that hash in your README, and move only when you choose to.
- **Hardware is last.** The control surface firmware is absent, so you cannot change anything on that side. You can only speak the protocol (Module 5). With the stand-ins done, the first hardware contact should be reading only.

Take the first row first. If you only tinker on your desk, the license asks nothing of you. That is the hobbyist case.

The second row is where people slip. Giving a friend a built binary is conveying. The friend is owed the source for exactly what you gave them. A link to the upstream repo is not enough if your version differs. Publish your fork.

The keep-the-notices rule lives in section 4 of `LICENSE`. Section 5 adds that your modified version must carry notices saying you modified it, with a date, and that the whole work must be licensed under the license. So: do not strip the headers from files you edit. Add a line saying what you changed and when.

The network row is the AGPL's special trait. Section 13 starts like this:

<CodeRef path="LICENSE" line={540} expect="13. Remote Network Interaction">

```text
  13. Remote Network Interaction; Use with the GNU General Public License.
```

</CodeRef>

For the KICK that matters if you add a network feature that outsiders use, such as a web page or a remote control app that talks to your modified build. Then you must offer those users your source. A device on your own bench that nobody else touches is not that case. Whether a specific setup counts is a question for the text and, if it matters, a lawyer.

The last row is about hardware. The license defines the information:

<CodeRef path="LICENSE" line={298} expect="Installation Information">

```text
  "Installation Information" for a User Product means any methods,
```

</CodeRef>

If you sold a consumer product running this firmware, owners would need what it takes to install their own modified builds. For a hobbyist sharing a repo and an image file, you are far from that. If you ever sell a device, talk to a lawyer first.

### Three more points

- **Your stand-ins join the work.** When you share a build, your `AudIO_constants`, `AudIO_juce` and the rest are part of the program. Plan to release them under the same license. Clean-room means you wrote them from the call sites, not from someone's closed copy.
- **Other licenses stay in force.** Third-party code keeps its own license. The upstream README has a table of them. One entry is not the AGPL, and it is the one most likely to surprise you:

<CodeRef path="Kick/README.md" line={49} expect="GPL-3.0-or-later">

```md
| ttymidi (Thiago Teixeira) | `apps/midiPort/src/ttymidi.c` | GPL-3.0-or-later |
```

</CodeRef>

  The Airwindows effects are MIT licensed (Module 7). MIT asks that you keep the copyright notice. The AudIO README lists its own third-party table.
- **Check what you reuse.** The root README shows product renders and photos. The AGPL covers the code. I do not know the license of the images. Do not copy them into your fork without checking.

The course itself is under a different license. The lesson text and images are CC BY-SA 4.0, as the course README says. That is separate from the AGPL on the code the lessons quote. If you reuse a lesson, keep the credit and share your changes under the same terms. If you reuse the quoted code, the AGPL applies to it.

## Trademarks

A license for code is not a license for names. The AGPL lets you copy and change the code. It does not hand you the right to use someone's brand. The text even leaves room for the author to decline trademark rights:

<CodeRef path="LICENSE" line={367} expect="Declining to grant rights under trademark law">

```text
    e) Declining to grant rights under trademark law for use of some
```

</CodeRef>

The product name sits in the root README:

<CodeRef path="README.md" line={5} expect="Behringer KICK">

```md
# Behringer KICK (BE 0700-AAM)
```

</CodeRef>

Behringer and KICK belong to MUSIC Tribe. This course is not made by or endorsed by them, and the course README says so. My advice, and it is general advice, not legal advice:

- **Do not ship a fork under their name or logo.** Pick your own name. Do not use "KICK" in the product name, the app title or an icon.
- **Rename the identity strings in the build.** The build files carry company and product names, for example the simulator's company name:

<CodeRef path="Kick/apps/kickem/CMakeLists.txt" line={5} expect="set(TargetCompany MUSICTribe)">

```cmake
set(TargetCompany MUSICTribe)
```

</CodeRef>

  The main app sets a vendor string in its package settings too:

<CodeRef path="Kick/apps/kick/CMakeLists.txt" line={163} expect="MusicTribe Innovation Pvt. Ltd.">

```cmake
set(CPACK_PACKAGE_VENDOR "MusicTribe Innovation Pvt. Ltd.")
```

</CodeRef>

- **Say plainly what it is.** A sentence such as "an unofficial community fork of the open-source firmware for the Behringer KICK" states a fact. A name or logo that looks like theirs suggests they made it. The first is generally safer than the second.
- **Do not reuse their artwork or product renders** unless a license says you can (see the point above).

## How to contribute back, and how to share a fork

**To upstream.** The root README invites pull requests with no membership needed:

<CodeRef path="README.md" line={53} expect="fork the repository and open a pull request">

```md
- **Contribute:** fork the repository and open a pull request. No membership needed. See the
```

</CodeRef>

The stand-ins are a good first contribution: a clean, licensed `AudIO_constants`, a small `AudIO_juce`, a serial class written from scratch. The repo cannot build without them. Be ready for the maintainers to say no or to have their own plan.

**To this course.** Lessons are Markdown files in `src/content/docs/course/`. Read `STYLE.md` first. If I got something wrong, the best correction names the file and line at the pinned commit and says what you ran. If you build any stand-in and it compiles, tell me. That result is worth more than anything in this lesson, because I have none.

**To share your fork.**

- Put it in your own repository. Keep `LICENSE` and every file header.
- In the README, say it is unofficial, name the upstream commit you forked from, list your changes, and list what you did not test.
- Release the stand-in modules separately with a short interface note, so the next person does not start from zero.
- Be honest about hardware. If you have not run it on a unit, write "not verified on hardware", as this course does.

## Try it yourself

This is a read-only checklist. It builds nothing, flashes nothing and needs no hardware. The goal is a one-page stand-in build plan in your own words, backed by lines you checked.

With the upstream clone at the pinned commit, run these and write one sentence for each result.

```bash
cd Kick
# 1. Confirm the three missing module names have no folder.
find .. -name "AudIO_juce*" -o -name "AudIO_constants*" -o -name "juce_serialport*" -o -name "juce_modules.cmake"
# 2. Who names them as dependencies?
grep -rn "AudIO_juce\|AudIO_constants\|juce_serialport" modules --include=*.h --include=*.cmake --include=CMakeLists.txt
# 3. Every use of the constants you must define.
grep -rn "AUDIO_SAMPLE_RATE\|AUDIO_BLOCK_SIZE\|AUDIO_NUM_" modules
grep -rhoE "(MIDI|POLYPHONY)::[A-Za-z_]+" modules | sort | uniq -c | sort -rn
# 4. Is any of them defined?
grep -rn "namespace MIDI\|namespace POLYPHONY\|define AUDIO_" modules ../AudIO
# 5. Every use of the serial classes.
grep -n "SerialPort" modules/input_events/input_events.cpp
# 6. Does the simulator target generate config.h?
grep -n "configure_file" apps/kickem/CMakeLists.txt apps/kick/CMakeLists.txt
```

Then fill in this table on paper, one row per hole:

1. The hole's name and which modules name it.
2. Each call site, with file and line.
3. The type and the constraints each site forces (compile-time constant, unsigned, template argument).
4. A value or design you would choose, and whether it has evidence or is a guess.
5. A test that would tell you the stand-in is right.

Finish with three answers.

- Which hole would you write first, and why?
- What is the smallest program that proves it, before you touch the UI?
- What would make you stop and change the plan?

## Words to know

| Term | Meaning |
|---|---|
| Fork | Your own copy of a project that you change and keep separately |
| Stand-in | Code you write to fill a missing piece, built from the needs of its callers |
| Call site | A line of code that uses a name; the evidence for what a missing piece must offer |
| JUCE module | A folder whose header holds a declaration block that lists its dependencies |
| CPM | A CMake tool that downloads dependencies by name and tag |
| Shim | A thin adapter that lets old code run in a new frame, like `AudioEffectX` |
| Overlay | A folder copied onto the finished root filesystem in a Buildroot image |
| Defconfig | The one-file recipe that tells Buildroot what to build |
| AGPL-3.0 | A copyleft license. Sharing a modified version requires sharing its source, and it adds a clause for network use |
| Convey | The license's word for giving others a copy of the program |
| Corresponding Source | The source needed to build and install the version you gave out |
| Installation Information | What an owner needs to install modified builds on a consumer device |
| SPDX identifier | A short standard tag in a file header that names its license |
| Trademark | A legal right in a name or logo, separate from the copyright license on code |
| Design, not built | My label for a sketch that I wrote and did not compile |
