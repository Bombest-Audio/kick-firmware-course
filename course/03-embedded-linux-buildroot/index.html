3. Embedded Linux and Buildroot

Module 3 of 12 · about 30 minutes · needs Modules 1 and 2

Module 2 ended with systemd starting an app. Where did that systemd come from? Who decided which audio tools are on the box, which kernel it runs, and how big the root partition is? One text file did. If you want a custom OS for the KICK, that file is where you start.

By the end you will be able to read the build recipe, name what each folder in the board directory does, explain why you cannot just run make on a Mac to get the app, and say what you would change at each step of the pipeline.

Analogy

A desktop distro is a supermarket. Somebody else stocked the shelves and you pick what you want. Buildroot is a recipe card plus a pantry list. You write down every ingredient and its exact version, and the machine cooks the whole meal from scratch. You get exactly what is on the card, nothing more.

What Buildroot is

Section titled “What Buildroot is”

Buildroot is a build system. You give it a config file. It downloads source code, compiles it all, and produces a complete Linux image: bootloader, kernel, and root filesystem. I am describing Buildroot from general knowledge here. The repository carries a full copy of the Buildroot tree, and its version is stamped in the top Makefile:

Makefile:95Not verified on hardware

So the KICK build is Buildroot 2021.02.3, copied into the repo.

Why would an embedded product use this instead of installing a desktop distro on the board? Four reasons, all general knowledge:

  • Size. A desktop distro carries thousands of packages. The KICK needs a few dozen.
  • Reproducibility. The same config gives the same image. A distro changes under you with every update.
  • Control. You pick the init system, the kernel, the libraries, and nothing else shows up.
  • No package manager on the device. The image is the product. You rebuild it, you do not patch it in the field.

The cost is time. Every build compiles everything. STACK.md in the upstream notes estimates one to two hours for a first build. That figure comes from the upstream notes, not from a build I ran.

The kernel config

Section titled “The kernel config”

A kernel config is a long list of on/off switches for features. I will point at one that matters for audio. The kernel is built as preemptible:

Linux-defconfig:5Not verified on hardware

Preemptible means a high-priority task can interrupt kernel code that is already running. That helps keep audio callbacks on time. This is general kernel knowledge. I have not measured the KICK’s latency, and a fully real-time kernel would use a different option.

The patches

Section titled “The patches”

The pinned fork is close to what the board needs but not exact, so the repo carries small patches. One of them edits the Goodix touchscreen driver, the same chip Module 2 met in the device tree:

003.goodix.c.patch:1Not verified on hardware

The U-Boot patch is bigger. It adds a new C file to the board directory, and that file reads two compressed images from an SD card and writes them to the eMMC:

001-sd-boot-burn-emmc.patch:9Not verified on hardware
001-sd-boot-burn-emmc.patch:71Not verified on hardware

So an SD card carrying rootfs.ext4.gz can install the OS onto the internal storage. The full flashing story belongs in Module 10. The installer also rewrites the partition table after it writes the rootfs, so I would not run it on a unit that holds data you care about (not verified on hardware). For now, note that this is board-specific code living in a patch, not in a package.

The rootfs overlay

Section titled “The rootfs overlay”

The defconfig names one folder as the overlay:

KTKick_defconfig:8Not verified on hardware

The rule, from general Buildroot knowledge: after all packages are installed into the target root, Buildroot copies the overlay folder on top, file for file. Same path means your file wins. New paths just appear.

That is how KICK adds its own pieces without touching Buildroot’s packages. The overlay holds the systemd units from Module 2, the Weston config, the audio config and the launcher script. For example, ktkick.service in the overlay is what runs the launcher:

ktkick.service:9Not verified on hardware

And the launcher expects the app to already sit at /usr/bin/KT_Kick:

kt_kick.sh:5Not verified on hardware

Notice what the image does not contain from the build above: the app binary itself. The overlay in this repository has the launcher, but I found no KT_Kick file in it. The app comes from a separate build, which is the next section.

The overlay also ships a small config that prepares writable layers for /etc and /var:

overlay-dirs.conf:4Not verified on hardware

The name “overlay” is overloaded here. The Buildroot rootfs overlay is a build-time copy. The overlay directories on kickstorage are a runtime layering trick (general Linux: a read-only lower layer plus a writable upper layer). They are two different things that share a word. I have not traced the mount units far enough to explain the runtime layering fully, so I leave it there.

Cross-compiling the app

Section titled “Cross-compiling the app”

Here is the fact that surprises people the first time. The machine that builds the code is not the machine that runs it. The build PC is the host. The KICK is the target. They use different CPUs, so code compiled on the host will not run on the target.

If you ran a normal compiler on your Mac, you would get an Apple-silicon or Intel program. The KICK’s i.MX 8M Mini cannot execute it. You also would not have the right libraries: the headers for ALSA, the GPU library and the Wayland client must match what is on the box.

A cross-compiler runs on the host and emits target code. A toolchain file tells CMake to use it. The pieces together are often called an SDK, short for software development kit: compiler, headers and libraries, all matched to one image. The upstream notes say Buildroot can produce one with make sdk. That command does not appear in any script I read, so I mark it as notes only.

The repo’s helper script shows the contract. It reads the toolchain file from an environment variable and configures CMake with it:

buildApp.sh:2Not verified on hardware
buildApp.sh:6Not verified on hardware

Then Ninja does the compile, and the result is copied up to the repo root under the name the launcher expects:

buildApp.sh:7Not verified on hardware
buildApp.sh:8Not verified on hardware

The continuous-integration script shows the same idea with a fixed path. It unpacks an SDK tarball and points CMake at the toolchain file inside it:

azure_build.sh:31Not verified on hardware

The upstream notes add two cautions. The prebuilt SDK tarball was removed from the open release, and buildApp.sh copies a file named KT_Kick that the CMake targets may not produce under that name, so you may need to rename the output yourself. Neither point is something I ran.

How does KT_Kick reach the device? From the upstream notes, two ways: copy it over SSH to a running unit, or bake it into an image. The repo has a transfer script for the first. I have not tried either.

Not verified on hardware

I do not claim that make KTKick_defconfig && make finishes, that the image boots, or that the app starts. The upstream notes also list missing private repos and removed assets that block a clean build. Check the upstream notes before you plan a build.

Why pinned forks cut both ways

Section titled “Why pinned forks cut both ways”

Every source here is pinned to a commit: kernel, U-Boot, trusted firmware. That gives you three things.

  • Same input, same output. A colleague who builds next year gets the same kernel.
  • No surprise regressions. An upstream change cannot break audio overnight.
  • A known base to patch. The three kernel patches apply cleanly because the base never moves.

It costs you too. The kernel is a vendor fork at one frozen point. Security fixes and new drivers from newer kernels do not arrive unless somebody rebases the fork and re-tests the board. A frozen kernel also ages out of what the compiler and tooling support. That is general embedded experience, not something this repo proves, but the pin on line 14 of the defconfig is the evidence that the freeze exists.

For a custom OS, the decision is yours: stay frozen and safe, or move the pin and own the testing.

Where a custom OS changes things

Section titled “Where a custom OS changes things”

Each step in the picture has a place where you can make a different choice.

Step What you could change Risk to watch
Defconfig Drop the X server and unused packages. Add your own. Removing something the app links against. Rebuild and boot-test.
Toolchain Pick and record a specific compiler. Mismatch with the app’s SDK. Build both from the same toolchain.
Kernel pin Move to a newer Variscite commit. The three patches may no longer apply.
Kernel config Change preemption model, drivers, logo. Config switches interact. Change one at a time.
U-Boot Restore a boot delay for recovery work. You lose the fast-boot behavior from Module 2.
Rootfs overlay Replace units, scripts and configs. A typo in a unit can leave the box without a UI.
genimage Resize partitions, change the layout. The mount units must still point at real partitions (see Module 2’s open question).

The overlay is the lowest-risk place to start. You change text files, rebuild, and the diff is small.

Check yourself

Section titled “Check yourself”

1 What is the main job of KTKick_defconfig?

  • A It is the compiled firmware that gets flashed
  • B It is the single recipe that tells Buildroot what to fetch, build and package
  • C It stores the user’s project files
  • D It is the app’s CMake file
Show answer

B. Buildroot reads the defconfig and builds the bootloader, kernel and root filesystem from it. Nothing in it is compiled output.

2 Why can you not run a normal build on a Mac and copy the result to the KICK?

  • A The KICK has no filesystem
  • B The Mac cannot run CMake
  • C The Mac builds for its own CPU, and the KICK has a different 64-bit ARM chip and different libraries
  • D Ninja only works on Linux
Show answer

C. Host and target differ. A cross-compiler plus a matching toolchain file produces code for the target.

3 What does the rootfs overlay do?

  • A Mounts a writable layer at runtime on every boot
  • B Copies its files on top of the built root filesystem at build time
  • C Compresses the kernel
  • D Replaces U-Boot
Show answer

B. The Buildroot overlay is a build-time copy. The runtime overlay directories on kickstorage are a separate thing that shares the word.

4 What is the main trade-off of pinning the kernel to one commit?

  • A Builds become random
  • B Builds are reproducible, but the kernel stays frozen and misses newer fixes unless someone rebases it
  • C The kernel cannot be patched
  • D The app cannot start
Show answer

B. A pin gives repeatable output and a stable base for patches. The cost is that updates from newer kernels are your job.

5 Where does the KT_Kick binary come from?

  • A It is built by Buildroot as a package
  • B It is already in the rootfs overlay
  • C It is built by a separate CMake and Ninja cross-compile and then copied to /usr/bin
  • D It is downloaded by U-Boot
Show answer

C. buildApp.sh produces KT_Kick outside Buildroot. The overlay only ships the launcher script that expects it at /usr/bin/KT_Kick.

Words to know

Section titled “Words to know”
Term Meaning
Buildroot A build system that produces a complete embedded Linux image from a config file
Defconfig A short config file listing only the options that differ from the defaults
Cross-compile Compile on one kind of machine (host) for another (target)
Host / target The machine that builds, and the machine that runs the result
Toolchain The compiler, linker and C library used to build code
SDK A toolchain plus matching headers and libraries for one image
Toolchain file A CMake file that points the build at a cross-compiler
Pin Fixing a dependency to an exact version or commit hash
Fork A copy of a project that its owner maintains separately
Patch A small diff applied to source code during the build
Rootfs overlay A folder copied onto the built root filesystem at build time
genimage A tool that writes partitions and disk images from a layout file
Ninja A fast build runner that CMake can drive
