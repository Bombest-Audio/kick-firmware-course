12. Fork it: build your own

Module 12 of 12 · about 40 minutes · needs Modules 3, 4 and 7

You have read the whole machine. Now the real question: can you change it and run your change?

This lesson is the plan, not the proof. I have not built any of it. I compiled nothing for this lesson, I ran no CMake, and every code sketch below is design, not built. What I did was read files at the pinned commit with git show and grep, and check every cited line. Where I guess, I say so.

By the end you will be able to list exactly which pieces a fork must write before it can compile, say what each piece has to provide, sketch the three kinds of change this course prepared you for, and explain in plain words what the AGPL-3.0 asks of you when you share the result.

Analogy

You inherit a family recipe binder. Most pages are there and readable. Four pages were torn out because the printer would not let the family reprint them. The dishes that need those pages cannot be cooked as written. But the other pages say “add the stock from page 12”, so you can work out what page 12 must have been, and write your own. That is a fork today. You rebuild the torn pages, then you start inventing new dishes.

What I conclude

Section titled “What I conclude”

The simulator was written for an older version of the input path. Treat it as a design to copy, not a tool to run. The better route is the one Module 5 described as Option A: skip the wire, build a packet struct yourself, and fire the real dispatch signal from the message thread. You get a simulator by writing about a hundred lines that feed the right signal, not by fixing the old one.

The stand-in plan

Section titled “The stand-in plan”

A stand-in is code you write to fill a hole, so the rest of the program can compile and run. You cannot copy the original, because you do not have it. But you have every caller. The callers tell you what the hole must hold.

The method is plain:

  1. grep for every use of the missing name.
  2. For each use, write down the type it needs, whether it must be a compile-time constant, and the operations it calls.
  3. Build the smallest thing that satisfies all of them.
  4. Mark every value you chose without evidence.

I did steps 1 and 2 for four holes. Step 3 is yours. Every value I propose is a guess unless I cite a line.

A recommended order of work

Section titled “A recommended order of work”

Start where a mistake costs the least, and let each step prove the one before it.

A few rules for the order:

  • Simulator first means the goal, not the first task. The first real work is the stand-ins. Do them one at a time and compile after each. When the first one lets one more module compile, you have evidence the method works.
  • One change at a time. Config switches interact (Module 3). A fork with five changes and one failure teaches you nothing.
  • Pin your base. Fork from the pinned commit, write that hash in your README, and move only when you choose to.
  • Hardware is last. The control surface firmware is absent, so you cannot change anything on that side. You can only speak the protocol (Module 5). With the stand-ins done, the first hardware contact should be reading only.

What it asks of you

Section titled “What it asks of you”
What you do What you owe Where in the text
Build, modify and run it for yourself and share nothing Nothing to publish Section 2, LICENSE line 152
Give anyone a copy of your version (a friend, a download, a release) The source of your version under the same license, the copyright and license notices left intact, and a notice that you changed it Sections 4, 5 and 6, lines 185, 198, 233
Run a modified version that other people use over a network Offer those users the source of your version Section 13, line 540
Ship a consumer device with it All of the above, plus the information needed to install modified versions on that device “Installation Information”, line 298

Take the first row first. If you only tinker on your desk, the license asks nothing of you. That is the hobbyist case.

The second row is where people slip. Giving a friend a built binary is conveying. The friend is owed the source for exactly what you gave them. A link to the upstream repo is not enough if your version differs. Publish your fork.

The keep-the-notices rule lives in section 4 of LICENSE. It says to keep intact the notices that state the license applies, and the notices of the absence of any warranty, and to give recipients a copy of the license. Section 5 adds that your modified version must carry notices saying you modified it, with a date, and that the whole work must be licensed under the license. So: do not strip the headers from files you edit. Add a line saying what you changed and when.

The network row is the AGPL’s special trait. Section 13 starts like this:

LICENSE:540Not verified on hardware

For the KICK that matters if you add a network feature that outsiders use, such as a web page or a remote control app that talks to your modified build. Then you must offer those users your source. A device on your own bench that nobody else touches is not that case. Whether a specific setup counts is a question for the text and, if it matters, a lawyer.

The last row is about hardware. The license defines the information:

LICENSE:298Not verified on hardware

If you sold a consumer product running this firmware, owners would need what it takes to install their own modified builds. For a hobbyist sharing a repo and an image file, you are far from that. If you ever sell a device, talk to a lawyer first.

Check yourself

Section titled “Check yourself”

1 Why does even the desktop simulator need the AudIO_constants and AudIO_juce stand-ins?

  • A The simulator plays audio through AudIO_juce directly
  • B The UI sits on modules that depend on common and audio_interface, which name those two missing modules
  • C The simulator CMake file includes them by path
  • D It does not need them; only the device app does
Show answer

B. kick_ui rests on the engine, and the engine rests on interface, which depends on common and audio_interface. Those two name AudIO_constants and AudIO_juce, so every app target needs them.

2 How do you work out what a missing module must provide?

  • A Download a copy from the original server
  • B Guess from the module name and fix compile errors
  • C Collect every call site, and record each name, its type, and any compile-time constraint it forces
  • D Copy a similar unlicensed library
Show answer

C. The callers are the only specification you have. A template argument forces a compile-time constant. An array of 128 caps an index bound. Record each such constraint, and mark guesses as guesses.

3 You modify the app, build it, and use it only on your own bench. What does the AGPL ask you to publish?

  • A The full source, within 30 days
  • B Nothing, because you have not conveyed it to anyone
  • C Only the files you changed
  • D A notice on a website
Show answer

B. Section 2 lets you make, run and propagate covered works that you do not convey, without conditions. The duties start when you give copies to others or let others use it over a network.

4 You add a web page that lets other people control your modified build over the network. What does section 13 add?

  • A Nothing, because a web page is not a copy
  • B You must offer those users the source of your version
  • C You must remove the license headers
  • D You must register the page with the Free Software Foundation
Show answer

B. Section 13 says a modified version that supports remote interaction must offer the users interacting with it an opportunity to receive its Corresponding Source. That is the network clause that makes the AGPL different from the plain GPL.

5 Can you ship your fork as "KICK Pro" with a look-alike icon, because the code is under the AGPL?

  • A Yes, the AGPL covers the name
  • B Yes, if you keep the copyright headers
  • C No, a code license does not give you the right to use the brand; pick your own name
  • D Only if you also publish the source
Show answer

C. Copyright license and trademark rights are separate. The code is free to change under the AGPL. The names Behringer and KICK belong to MUSIC Tribe. This is general advice, not legal advice.
