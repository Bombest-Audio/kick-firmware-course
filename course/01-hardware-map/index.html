1. The hardware map

Module 1 of 12 · about 20 minutes · no prerequisites

A KICK looks like one instrument. Inside, it is two computers sharing a box, and they talk over one wire. The big one runs Linux and the KICK app. The small one reads the pads, knobs and buttons and lights the LEDs. Almost every feature you can think of crosses that wire, so it is the first thing to understand.

By the end of this module you will be able to name every chip or port the app talks to, say which kind of connection it uses, and find the line of code that opens it.

Analogy

Think of a band with a conductor and a stage crew. The main computer is the conductor: it knows the song, the tempo and what sound to make. The control surface MCU is the stage crew: it watches the floor, reports every footstep, and flips the lights when told. They never share a brain. They only pass short notes back and forth.

Two ways chips talk

Section titled “Two ways chips talk”

Almost every row in that table uses one of two kinds of wire. Knowing the difference explains a lot of the code.

UART: one conversation, agreed speed

Section titled “UART: one conversation, agreed speed”

A UART is a two-wire serial link. One wire carries bytes each way, and there is no shared clock. Instead, both sides agree ahead of time on a speed, called the baud rate, and each byte is wrapped in a start bit and a stop bit so the receiver can find the edges.

The app opens the control-surface link like this:

input_events.cpp:61Not verified on hardware

Read it as “230400 bits per second, 8 data bits, no parity, 1 stop bit.” That setup is called 8N1. Each byte costs 8 data bits plus a start and a stop bit, so 10 bits on the wire. At 230400 bits per second that is 23,040 bytes per second, about 23 kilobytes. That is plenty for button presses and LED colors, and far too small for audio. This is why the audio never travels over this link.

I2C: a shared hallway with addresses

Section titled “I2C: a shared hallway with addresses”

I2C is a two-wire bus that many chips share. Every chip has an address, like an apartment number, and the main computer says “number 12, here is your data.” The CV/Gate chip answers to address 0x0c:

kick_I2c.cpp:34Not verified on hardware

To set a voltage, the app sends three bytes. The first byte holds the command and the channel, and the other two hold a 12-bit value split across them:

kick_I2c.cpp:140Not verified on hardware

Work one through. A 12-bit value runs from 0 to 4095, so the middle is 2048, which is 0x800 in hex. The top 8 bits are 0x80 and the bottom 4 bits are 0x0. For channel 0 the three bytes are 30 80 00. For 0x0ABC they would be 30 AB C0. The low nibble of the last byte is unused padding, which is why the code shifts left by 4.

I am not naming the chip. The code never says which DAC it is, and guessing the part number would be a mistake. If you plan to change this protocol, get the schematic first.

The wire between the two computers

Section titled “The wire between the two computers”

The control surface link is the busiest connection in the machine, so it has its own small language. The PktMgr code defines eight kinds of packet:

PktMgr.hpp:34Not verified on hardware

That list is a good summary of what the control surface does: it reports pads, buttons, knobs and a slider, it accepts LED commands, and it carries MIDI and CV traffic of its own. A packet is a short frame that starts with the two letters M and T, so the receiver can find the start of a message even if it joins the conversation halfway through:

The receiver checks for M, then T, then reads the type, direction, command and size, then the data bytes and the checksum. The size byte counts the data bytes plus one for the checksum, as Module 5 shows:

PktMgr.cpp:44Not verified on hardware

The checksum, called a CRC, lets the receiver throw away a packet that got scrambled on the way. You will meet it again in Module 5.

Who runs the other computer?

Section titled “Who runs the other computer?”

The small computer has its own program, and that program is not in this repository. I know it exists for two reasons. The app’s update code can send a new program to it over the same wire:

kick_FirmwareUpdate.cpp:112Not verified on hardware

And the packet code stops at the wire: there is a state machine for receiving, but nothing that says what happens inside the chip on the other end. Treat the control surface MCU as a black box with a known protocol. That is enough to write a replacement for the main computer’s side, and it is the reason a custom OS is realistic even without that firmware.

What is not here

Section titled “What is not here”
  • The control surface firmware. Only the main computer’s side of the link is public.
  • Camera and gesture code. The Linux build includes a driver for an OV5640 camera sensor (Linux-defconfig:373), but I found no app code, model or inference library in the repository. The feature exists on the box and in marketing. The software that makes it work is not in this release.

A note on the main chip. The board directory is named imx8mm_var_som, and the bootloader script checks for the i.MX 8M Mini platform (imx8-bootloader-prepare.sh:11). From NXP’s public datasheet, not from this repository, that chip has no dedicated neural processor, so any on-device gesture recognition would run on the regular CPU cores unless the camera module has its own hardware. I have not seen a unit, so I can’t say which.

Check yourself

Section titled “Check yourself”

1 Why does audio not travel over the UART link to the control surface?

  • A The UART only supports MIDI
  • B At 230400 baud it carries about 23 kilobytes per second, far too little for audio
  • C The UART is encrypted
  • D Audio uses the camera link
Show answer

B. Each byte takes 10 bits on the wire with an 8N1 setup, so 230400 bits per second is 23,040 bytes per second. Audio goes through ALSA to a codec instead.

2 The CV DAC takes a 12-bit value of 0x0ABC on channel 0. Which three bytes does the app send?

  • A 30 0A BC
  • B 30 AB C0
  • C 00 AB C0
  • D 30 BC 0A
Show answer

B. The first byte is 0x30 OR the channel. The second is the value shifted right by 4 (0xAB). The third is the value shifted left by 4, masked to the top nibble (0xC0).

3 What is the job of the letters M and T at the start of a packet?

  • A They name the packet type
  • B They let the receiver find the start of a frame
  • C They hold the checksum
  • D They set the baud rate
Show answer

B. The receiver waits for M, then T, before it starts reading the type, direction, command and size fields.

4 What can you say for certain about the camera feature from this repository alone?

  • A It runs a hand-tracking model on the GPU
  • B The Linux build includes a driver for an OV5640 sensor, but no app code for it
  • C It is controlled by the MCU over the PktMgr link
  • D It is disabled in the kernel
Show answer

B. The kernel config enables the OV5640 driver. A search of the app, audio engine and protocol code found no camera or model code.

5 Why is writing a custom OS still realistic without the control surface firmware?

  • A The firmware is easy to replace
  • B The wire protocol is public, so the main computer can speak it without knowing the MCU internals
  • C The MCU is not needed
  • D The firmware is bundled in the Linux image
Show answer

B. PktMgr defines the frame format and packet types for the main computer side. The MCU can stay a black box as long as you send and receive the same packets.

Words to know

Section titled “Words to know”
Term Meaning
SoC System on a chip: CPU, memory controller and many peripherals in one package
MCU Microcontroller: a small chip with its own program, often used to watch buttons and sensors
UART Two-wire serial link with an agreed speed and no shared clock
Baud Signal changes per second. Here it is the same as bits per second
I2C Two-wire shared bus where each chip has an address
DAC Digital to analog converter. Turns a number into a voltage
ALSA The Linux sound system
Device node A file in /dev that stands for a piece of hardware, like /dev/i2c-3
Device tree A data file that tells the Linux kernel what hardware exists and at which addresses
CRC A checksum that detects scrambled data
