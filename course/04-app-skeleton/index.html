4. The app skeleton

Module 4 of 12 · about 35 minutes · needs Module 2

The KICK app is about 255 lines of startup code sitting on top of a pile of modules. If you open the repository cold, the pile is what you see first. This lesson gives you the map. You will know where the program starts, which thread does what, how a screen gets built, and where a new screen would plug in.

By the end you will be able to trace one tap on the home screen from the first signal to the screen becoming visible, naming each file and each thread on the way.

Analogy

A restaurant. The front of house has one host who talks to every guest and must never walk away from the door. The kitchen has cooks who can take as long as the dish needs. The host hands orders to the kitchen and asks to be told when the plate is ready. The host is the message thread. The cooks are worker threads. The rule that keeps the restaurant alive is simple: the host never cooks.

What JUCE is, and the two threads that matter

Section titled “What JUCE is, and the two threads that matter”

JUCE is a C++ framework for audio software and its user interfaces. It gives you windows, buttons, drawing, timers, audio device access and a shared event system. Most commercial plugins are built on it. The KICK app is one JUCE program (general knowledge about JUCE, plus the code below that uses it).

Two threads matter for this lesson.

  • The message thread. One thread runs the event loop. Every tap, every repaint, every timer callback and every screen change runs here, one at a time. If code on this thread takes 200 ms, the screen freezes for 200 ms. So the rule is: never block the message thread. No long file reads, no waiting on a lock another thread holds, no sleeping.
  • The audio thread. The audio driver calls your code on its own high-priority thread, over and over, with a small buffer to fill. If you miss the deadline you get a click or a dropout. Rules for this thread are stricter still: no memory allocation, no locks, no file access (general real-time audio knowledge). Module 6 covers it in depth.

The code shows both. The sample player registers a callback with the audio device manager:

And its getNextAudioBlock is the function the audio thread calls to get the next buffer (JUCE’s AudioSource contract, general knowledge):

Everything else in this lesson runs on the message thread, plus a thread pool for jobs that must not block it.

Singletons: easy to reach, hard to see

Section titled “Singletons: easy to reach, hard to see”

A singleton is an object of which exactly one exists, reachable from anywhere. The KICK uses two patterns for them.

The first is the accessor function that builds the object on first call. Settings:

kick_settings.cpp:26Not verified on hardware

And the audio interface, same shape:

mt_audio_interface.cpp:128Not verified on hardware

A static local variable inside a function is built the first time execution reaches it, once, and C++11 guarantees that is thread-safe (general C++ knowledge). That is why mt::getSettings(); alone in initialise does something: it forces the build at a time the author chose, instead of at some random first use. The declaration the rest of the code sees is one line:

kick_settings.h:251Not verified on hardware

The second pattern is a class with a static Instance(). The home component works this way, and its constructor is private so nobody else can make one:

kick_AppHome.h:34Not verified on hardware

The trade-off

Section titled “The trade-off”

The upside is real. Any file can write mt::getAudioInterface() and get the engine. No plumbing. Look at how many places do exactly that. The LED module grabs both singletons as member initializers:

kick_leds.h:69Not verified on hardware
kick_leds.h:70Not verified on hardware

The cost is that the dependency is invisible. KickLEDs needs the engine and the settings to work, but you cannot see that from its constructor signature. To know what a class touches, you have to read its body. Two more problems follow:

  • Testing is harder. You cannot swap the real audio interface for a fake one in a test, because the class goes and gets the real one itself.
  • Order matters, and nothing enforces it. If one singleton’s constructor calls another, the chain works until someone changes it.

None of this is wrong for a device that ships as one program. It is a speed-of-development choice. If you plan to write unit tests for your own screens, the cheapest fix is to hand your class the objects it needs through its constructor, and have the caller pass mt::getAudioInterface().

Signals

Section titled “Signals”

Screens do not call each other. They send a signal, and KickHome listens. The signals are static members, from the sigslot library in 3rdParty:

kick_IScreen.h:71Not verified on hardware

A signal is a list of functions. Calling the signal calls every function connected to it. It is the observer pattern with a short name. KickHome connects to sigScreenOpen in its constructor:

kick_AppHome.cpp:144Not verified on hardware

The benefit: a screen that wants to open another only needs the enum value, not a pointer to the other screen. The cost matches the singleton problem. To find who opens a screen, you search for the enum name across the repo, because there is no direct call to follow.

Thread hops

Section titled “Thread hops”

The batch above does something worth looking at closely. It runs on a thread pool, then immediately hops back to the message thread:

kick_AppHome.cpp:210Not verified on hardware
kick_AppHome.cpp:211Not verified on hardware

The pool is a global with five worker threads:

kick_utils.h:29Not verified on hardware

The pattern, in general, is:

  1. The message thread hands a job to a worker (addJob).
  2. The worker does the slow part, such as reading a file or decoding data.
  3. The worker cannot touch the UI. JUCE components belong to the message thread. So it hands a small piece of work back (callAsync), which runs on the message thread when its turn comes.

Now compare that with what the screen batch really does. Look at lines 210 and 211 together. The pool job contains nothing slow. Its only statement is the callAsync, and all 27 screen constructors sit inside that closure. So they run on the message thread, not on the worker. The pool hop only changes when they run: after the current work finishes, not before. It defers the batch. It does not move any work off the message thread. If a screen constructor is slow, it will still freeze the display for that long. That is an observation about the code. I did not time it.

One more detail of the pool. It is declared static at namespace scope in a header. In C++, that gives each source file that includes the header its own private copy (general C++ knowledge: static gives internal linkage). That means “the” pool may be several pools of five threads each, depending on how many files include it. I have not counted them.

Monolith or several programs?

Section titled “Monolith or several programs?”

Open Kick/apps and you see many folders. They are not all part of one image. They fall into three groups.

The monolith. apps/kick is the program this lesson just walked through. It builds the engine, the UI and the hardware control all inside one process. Main.cpp calls mt::getAudioInterface() directly, with no messaging layer between the UI and the engine. The boot script from Module 2 starts a binary called KT_Kick. Monolith versus several processes

Section titled “Monolith versus several processes”
One process Several processes
A crash in the engine Takes down the whole app The supervisor can notice and restart one piece
Speed of a call between UI and engine A function call A message over a socket
Debugging One debugger, one log Several logs, startup order, ports
Memory One address space Isolation, at a cost per process

The supervisor does appear built for the multi-process case: it starts a heartbeat monitor on boot.

Where a new screen goes

Section titled “Where a new screen goes”

I can only list what the code shows. Adding a screen touches four places.

  1. The enum. Add a name to Screen in kick_IScreen.h. The existing list ends with Inserts and Temp:
kick_IScreen.h:64Not verified on hardware
  1. The class. Write a component that also inherits kick_ui::IScreen and passes its enum value to the base constructor, the way the grid view does:
kick_AppGrid.cpp:141Not verified on hardware
  1. Registration. Add one screenAdder line to the batch in KickHome, next to line 240.
  2. A way to reach it. Something has to send sigScreenOpen( Screen::YourNewScreen ). That could be a menu entry or a button handler.

Overriding requiresControlBar and requiresStatusBar decides which bars show. The source files in kick_ui are picked up by CMake as part of the module (I did not verify how the globbing works, so check that a new file lands in the build before you trust it).

Customization pointers

Section titled “Customization pointers”
  • Add a screen: the four steps above. Start by copying a small existing screen.
  • Change startup order or the first screen: KickHome’s constructor, around lines 191 and 207.
  • Change what happens at boot: initialise in Main.cpp.
  • Turn the pool-based batch into something real: move the slow part of a screen’s setup into the addJob body and keep only the setVisible and addChildComponent calls inside the callAsync.
  • Reduce hidden dependencies: take the engine and settings in constructors instead of calling the global accessors.

Check yourself

Section titled “Check yourself”

1 What is the one rule for the message thread?

  • A Never create components on it
  • B Never block it with slow or waiting work
  • C Only run audio code on it
  • D Run exactly one job per second
Show answer

B. Every tap, repaint and screen change runs on this one thread. If it blocks, the screen freezes.

2 Why does initialise call mt::getSettings(); and ignore the result?

  • A To print the settings to a log
  • B To force the singleton to be built at a chosen time
  • C To save the settings to disk
  • D To check that the audio device is plugged in
Show answer

B. A function-local static is built the first time the function runs. Calling it early decides when the build happens.

3 What is the main cost of the singleton accessors such as mt::getAudioInterface()?

  • A They are slower than a normal function
  • B They cannot be called from the UI
  • C A class depends on the engine without saying so in its constructor, which also makes tests harder
  • D They create a new engine every call
Show answer

C. The dependency is real but hidden inside the function body. Tests cannot swap in a fake easily, and readers must scan the code to see what a class touches.

4 KickHome builds most screens inside a pool job that immediately calls callAsync. What does that actually achieve?

  • A It runs the screen constructors on a worker thread
  • B It builds each screen only when the user taps it
  • C It defers the batch until after the first screen is up, but the constructors still run on the message thread
  • D It lets screens be built in parallel
Show answer

C. The only statement in the pool job is the callAsync, so the constructors inside it run on the message thread, just later.

5 What does opening a screen do in KickHome, once the screen exists?

  • A Creates the screen from scratch and adds it to the window
  • B Hides every screen, then makes the chosen one visible and adjusts the bars
  • C Starts a new process for that screen
  • D Reloads the whole app
Show answer

B. All screens are children of the home component. setupLoadScreenVisibility hides them all and shows one.

Words to know

Section titled “Words to know”
Term Meaning
JUCE A C++ framework for audio apps and plugins. Gives windows, drawing, timers and audio device access
JUCE module A unit of source that CMake registers by name, such as kick_ui
Message thread The one thread that runs the UI event loop. Must never block
Audio thread The driver-called thread that fills audio buffers. Real-time rules apply
Thread pool A fixed set of worker threads that run queued jobs
callAsync JUCE call that queues a closure to run later on the message thread
Singleton An object of which only one exists, reachable from anywhere
Signal / slot A list of functions called when the signal fires. The observer pattern
IScreen The base class every screen implements
Screen The enum of every page the UI can show
Monolith One program that holds all the parts, versus several cooperating processes
Supervisor A process whose job is to start and watch others
