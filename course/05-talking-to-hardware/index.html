5. Talking to the hardware

Module 5 of 12 · about 45 minutes · needs Module 4

Every pad you hit, every knob you turn and every button light you see goes through one thin wire. On one end is a small microcontroller, the MCU, which scans the pads. On the other end is the KICK app. Between them runs a short, strict language.

By the end of this lesson you will be able to read one frame of that language byte by byte, compute its checksum by hand, say which thread touches it at each step, and trace a pad press from the serial port to the line that starts a sample.

One limit up front. The MCU firmware is not in this repository. Everything I say about what the MCU sends comes from what the app expects to receive. The one exception is the packet class itself, which is shared. The same source file has a branch for the MCU build:

PktMgr.cpp:3Not verified on hardware

Analogy

Two people pass notes through a slot in a wall. Every note uses the same envelope. It opens with a two-letter stamp so the reader knows a note began. Then it says what kind of note it is, what it asks for, and how long the contents are. Then the contents. Then a check digit the writer worked out from everything before it. The reader works out the same digit. If the two digits differ, the note goes in the bin. Nobody writes back to say it was bad.

The size byte counts the CRC

Section titled “The size byte counts the CRC”

This is the detail Module 1 glossed over. The size field is not the number of data bytes. It is the number of data bytes plus the CRC byte. The sender adds one on line 169 above. The receiver subtracts it back off when it collects data:

PktMgr.cpp:87Not verified on hardware

So a frame with 3 data bytes has a size field of 4 and is 10 bytes long: 2 start, 3 header, 1 size, 3 data, 1 CRC. The general rule is data + 7.

The frame has one extra byte on the way in

Section titled “The frame has one extra byte on the way in”

The reader in the app expects frames from the MCU to be one byte longer than the frames the app sends. Look at how it computes the length of a frame it is about to read:

byteArray[5] is the size field. The size field already includes the CRC, so size + 6 would be the whole frame. The code uses size + 7. Then, while feeding bytes to the state machine, it skips the last one:

That last byte is read from the buffer and thrown away. I infer that the MCU ends every frame with one extra byte after the CRC. There is a hint in the state enum, which has a member after EN_FRM_STATE_CRC called end-of-frame:

And on the send side, a line that would append a newline is commented out:

So frames the app sends have no trailer, and frames the app receives are expected to have one. If the MCU left it off, the length check at line 184 would fail and the frame would be dropped (more on that under errors). I could not confirm the trailer value, because the MCU code is not here.

The checksum

Section titled “The checksum”

The CRC is a one-byte checksum. Here is the whole routine. Four lines carry the idea. It starts at 0xFF:

PktMgr.cpp:132Not verified on hardware

For each byte, it XORs the byte into the running value:

PktMgr.cpp:138Not verified on hardware

Then it does eight rounds of shifting. If the top bit is set, it shifts left and XORs with 0x31:

PktMgr.cpp:141Not verified on hardware
PktMgr.cpp:142Not verified on hardware

If the top bit is clear, it only shifts left. The result after the last byte is the CRC. The receiver runs the same routine over everything it has collected before the CRC byte and compares:

PktMgr.cpp:100Not verified on hardware

Why bother with the shift-and-XOR dance? A plain sum of bytes would miss two errors that cancel out. This routine treats the bytes as one long binary number and keeps the remainder of a division, which makes it catch bursts of flipped bits. That is general knowledge about CRCs, not something the repository explains.

Four things in this machine surprised me.

  • The scratch buffer is a function-local static. Every byte is also stored in a shared vector, and the CRC is computed over it. Because it is static, it survives between calls and is shared by every CPktMgr object.
PktMgr.cpp:37Not verified on hardware
  • The machine never resets itself. After the CRC state it stays in the CRC state. Only Init and ClearReceiver put it back to INIT_1. The caller has to call one of them after every frame, good or bad.
PktMgr.cpp:32Not verified on hardware
  • INIT_2 does not fall back. If the byte after an M is not T, the machine stays in INIT_2 and keeps storing bytes. It never goes back to hunting for M. In practice this does not bite, because the app’s reader only feeds it bytes after checking that the buffer starts with M and T (see below).
  • The end-of-frame state has no code. The enum has EN_FRM_EOF, but the switch has no case for it. That fits the idea that the trailer byte is dropped by the caller before it ever reaches the machine.

The type, the direction and the command are the three header fields from the frame. data is the payload, widened from bytes to ints. It is the same shape in both directions: the sender fills one and BuildAndTransmitPacket turns it into bytes, and the reader builds one from bytes. Squeezing an int into one wire byte keeps only the low 8 bits (general C++ behavior when you push an int into a vector of chars), so a value above 255 would silently wrap.

It is the common currency of the program. The type is mentioned in 151 files at the pinned commit (git grep -l "HWMsg_t"). Every signal that carries a hardware event carries it by reference:

When things go wrong

Section titled “When things go wrong”

This is the part with the fewest guard rails. I read each failure path. Where I ran the packet class on my Mac to confirm, I say so.

Situation What the code does Where
Fewer than 6 bytes in a read Returns before reading. What the stream does with the unread bytes is inside juce_serialport, which I did not read input_events.cpp:159
A frame does not start with M T Sets the remaining length to 0, so everything left in that read is thrown away. There is no search for the next M input_events.cpp:184, :199
A frame is cut off at the end of a read Same branch as above. The partial frame is dropped, and its tail is not kept for the next read input_events.cpp:184

Let me expand on the first two rows, because they are the heart of “lost sync”. In many serial protocols, if you land in the middle of a frame you scan forward until you see the start stamp again. This reader does not do that. It trusts that every read begins at a frame boundary. If one byte is lost or one extra byte arrives, the rest of that read is gone. The next read gets a fresh chance, but only if it happens to start cleanly. The leading M T and the CRC are what keep garbage from being accepted, not what let the reader recover.

There is no negative acknowledgment to the MCU, no counter, and no log in a normal build. A bad frame just vanishes. If a pad press is lost this way, the MCU cannot know.

Edge cases I noticed, not run in the app

Two sizes the state machine does not handle cleanly. I tested the first one on the desktop with the scratch build of the packet class alone.

Size 1, meaning zero data bytes. BuildAndTransmitPacket writes size 1 for a message with no data. The reader’s DATA state only advances while the write position is below size minus 1, which is below 0. It never advances, so the CRC byte is swallowed as data and the flag never sets. In my scratch test, that frame was not accepted, and the next good frame after it was also rejected, because the shared scratch buffer still held the stale bytes. The frame after that was accepted. So one extra frame is lost. The app’s reader would then take its “frame error” branch and reset the state machine, but it would not clear the scratch buffer.

Size 0. The state machine jumps straight to the CRC state (line 79). The callback’s pop loop is while( size - 1 ), which does not stop at 0. I did not run this case in the app, so I will not predict what happens.

Both need an MCU that sends those sizes, and the app’s own commands always carry data. Keep the data count at one or more if you add a packet type.

One more limit to know before you add a packet. The receive buffer handed to the packet class is 20 bytes:

ComConfig.hpp:6Not verified on hardware

The DATA state checks the position against the frame’s size field. I did not find a check against that 20-byte buffer. So keep inbound frames small, well under 20 data bytes. Outbound frames have no such buffer. The send side builds a vector, so a long message such as setting all pad colours is fine on the way out.

Section titled “The handshake”

When the app opens the port it says hello, and later the MCU and the app exchange two small system messages. This is all SYSTEM-type packets, type 0.

Why it is built this way

Section titled “Why it is built this way”

A tiny, shared packet class. PktMgr has no dependencies and compiles on the MCU as well as on Linux. The README says so:

README.md:4Not verified on hardware

The benefit is that both sides agree on the framing because they run the same code. The cost is that the class is written for a small chip: fixed buffers, a single static scratch vector, and no help for the caller when something goes wrong.

One thread handles input end to end. There is no queue between the serial callback and the screens. The benefit is simplicity and ordering: events reach the UI in the order the bytes arrived, and no screen needs a lock. The cost, as noted, is that slow UI work delays port reads.

A dedicated send thread. The message thread must never block (Module 4). Writing to a port can block. So sends go through a queue to a thread whose only job is to wait and write. The benefit is that LED updates from any thread are safe and cheap to issue. The cost is a wake-up delay before each write, and a queue where I did not see a cap on its length.

A JSON detour in a monolith. It keeps one command format for the single-process and multi-process builds. It costs extra copying in the single-process one.

Add a new packet type

Section titled “Add a new packet type”
  1. The type enum. Add a name at the end of enumPacketType, after EN_PKT_TYPE_SLIDER. Do not reorder or insert in the middle: the numbers are the wire values, and the MCU has its own copy.
PktMgr.hpp:43Not verified on hardware
  1. The command enum. Add a command list in dcl_contracts.h, next to LedCmd, PadCmd and SliderCmd.
  2. A builder and a predicate. In DclContractsHelper, add a builder that calls prepareHWMessage (for outbound) and a predicate like isPadButtonMessage (for inbound).
  3. A handler. For a global effect, add a branch in KickHome::handleCommand. For a screen-specific effect, override handleCommand in the screen and make requiresHandleCommand return true.
  4. The MCU. The firmware has to send or understand the new type. That part is outside this repository.

Check yourself

Section titled “Check yourself”

1 A message has 3 data bytes. What is the value of the size byte in its frame?

  • A 3
  • B 4, because the size counts the data bytes plus the CRC byte
  • C 7, because the header is 7 bytes long
  • D 10, because that is the whole frame length
Show answer

B. BuildAndTransmitPacket pushes the data count plus PKTMGR_CRC_BYTE. The receiver collects size minus 1 data bytes and then reads the CRC.

2 Which bytes does the CRC cover?

  • A Only the data bytes
  • B The type and the command
  • C Every byte from the M through the last data byte, but not the CRC byte itself
  • D Every byte of the frame including the trailer
Show answer

C. CrcGen runs over the whole scratch buffer, which starts with M and ends with the last data byte. The CRC state compares the result with the incoming CRC byte and does not add that byte to the buffer.

3 The CRC of an incoming frame does not match. What does the app do?

  • A Sends a negative acknowledgment so the MCU resends
  • B Stops reading the port until it is reset
  • C Drops the frame, resets the receiver and carries on with the next frame in the read, with no trace in a normal build
  • D Passes the frame to the screens anyway and logs a warning
Show answer

C. The flag stays false, so the callback takes its frame-error branch and clears the receiver. The debug print is only compiled in when DEBUG_PRINTS is set, and the app never sends acks.

4 Which thread builds the outgoing frame and writes it to the port?

  • A The message thread, inside sendMessageToHardware
  • B The audio thread, so LEDs stay in time
  • C The thread that called sendCommandToDcl
  • D A worker thread named "Queue", fed by a lock-free queue
Show answer

D. sendMessageToControlSurface only enqueues and triggers an async wake-up. The "Queue" thread runs BuildAndTransmitPacket and the write, so nobody else waits on the port.

5 A read from the port starts with a stray byte, then a valid frame. What happens to the valid frame?

  • A The reader skips the stray byte and parses the frame
  • B The reader drops everything left in that read, because it only accepts a read that starts with M and T
  • C The state machine resyncs on the next M
  • D The CRC fails and the frame is retried
Show answer

B. The callback checks the first two bytes of the buffer and sets the remaining length to zero if they are not M and T. There is no scan forward for the next start stamp.

Words to know

Section titled “Words to know”
Term Meaning
MCU The microcontroller that scans the pads, knobs and buttons and drives the LEDs
UART A two-wire serial link with an agreed speed. Module 1 covers it
Frame One complete message on the wire, from the M to the CRC
Packet type The first field after the stamp. SYSTEM, BUTTON, LED, PAD, KNOBS, MIDI, CV or SLIDER
Size byte Data bytes plus one. The extra one is the CRC
CRC A one-byte checksum computed from every byte before it
State machine Code that holds a current state and decides what each new byte means from that state
HWMsg_t The struct that carries a decoded message: type, direction, command and a vector of data values
Handshake The short exchange at startup that tells each side the other is there
Trailer The extra byte the reader expects after the CRC on incoming frames. Its value is unknown here
Lock-free queue A queue many threads can add to without taking a lock
AsyncUpdater A JUCE helper that asks for a callback on the message thread
Stand-in A piece of code that plays the part of the hardware so you can test without it
